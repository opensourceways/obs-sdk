# 可观测接入指南

面向**基础设施各类业务**的接入指引：自研微服务、面向用户的开源软件、CI 资源与 CI workflow，都能在本文找到自己的路线。

---

## 1. 先选路线：你属于哪一类

| 范围 | 分类 | 判定方法 | 核心手段 | 典型对象 |
| --- | --- | --- | --- | --- |
| 微服务 | **自研微服务** | 代码由我们维护，用 Go / Python / Node / Java 之一 | 接入 obs-sdk（四个语言包），日志走 kv、指标自动补部署级 label | CLA `app-cla-server`、评审机器人 `review`、welcome 机器人 `robot-universal-welcome`、forum-reply-robot、账号 `om-webserver`、CVE `cve-manager-ng`、openeuler-easysearch 等自研服务 |
| | **开源软件** | 代码不是我们的，但有独立用户入口或对外服务 | 官方 exporter / 自带 `/metrics` + 黑盒拨测，必要时日志解析，不改代码 | Discourse、Etherpad、Mailman、FreshRSS、LightRAG、PDFMathTranslate、MirrorManager2、mirrorbits、mirrorlist-server、Xihe Gitea、oauth2-proxy、trivy、secrets-manager、COPR、fscrawler |
| CI | **CI 执行资源** | 为流水线提供运行能力，不关心某条流水线跑什么 | 原生 `/metrics` + 官方 exporter / sidecar + 平台统一采集（node-exporter、kube-state-metrics、npu-exporter）+ 拨测 | ARC runner / 执行机、buildkitd、squid 缓存、karmada、volcano、liqo、scheduler-plugins、git-cdn、smart-git-proxy、nginx-pypi-cache、NPU 卡池、SFS Turbo 共享盘、ingress-nginx |
| | **CI workflow** | GitHub Actions / CodeArts 上的流水线，有 run 生命周期与成功/失败语义，无常驻 HTTP 服务 | 作业级指标写 Pushgateway + 事件日志（workflow run 事件 / API） | `vllm-project/vllm-ascend` 的 `pr_test.yaml`（E2E）、`_selected_tests.yaml`（用例选择）、`schedule_image_build_and_push.yaml`（镜像）、`schedule_daily_test.yaml`（每日回归）
| | **Jenkins 任务** | 跑在 Jenkins 上的 Job / Pipeline，有构建号与结果，无常驻 HTTP 服务 | Jenkins Prometheus plugin 暴露 `/prometheus` + 日志解析；必要时用 Pushgateway 补作业级指标 | `src-openeuler`（GitCode）每个仓库的门禁工程 `trigger` → `x86-64` / `aarch64` → `comment`；`Infra/community_check_v2` 的 conflict / sanity / branch check；`build_chart_only`、`update_chart_version`、`publish_chart`、get-kubeconfig |

> 一条 CI workflow 跑在 CI 资源上：资源侧指标由平台统一采集，作业侧指标由流水线自己上报。按**观测对象**拆，不按仓库拆。

## 2. 自研微服务接入

代码由我们维护的服务——CLA 的 `app-cla-server`、评审机器人 `review`、账号 `om-webserver`、CVE 管理的 `cve-manager-ng` 等——都走这条路，不论用 Go / Python / Node / Java 哪种语言：直接引对应语言包，**不要自己拼日志库或指标库**。

指标与日志可以分开接，互不依赖。

### 2.1 指标接入

#### 2.1.1 配置环境变量

SDK 把四个部署级字段附加到每条时间序列：

| 字段 | 环境变量 | 缺省值 |
| --- | --- | --- |
| `service` | `OBS_SERVICE` | `unknown` |
| `env` | `OBS_ENV` | `unknown` |
| `instance` | `OBS_INSTANCE` | hostname（k8s 下即 pod 名） |
| `community` | `OBS_COMMUNITY` | `unknown` |

取值优先级：**显式参数 > `OBS_*` 环境变量 > 缺省值**。四语言 SDK 读同一套变量名，部署模板不因语言而异。

> ⚠️ **四个字段恒非空，部署模板里别留空值。** 空值不会输出成 `unknown`，而是让该 label 整段消失——按 `service` 过滤的查询直接查不到这条 series，且不报错。

以 welcome 机器人为例，在 `Open-Infra-Ops/helm-chart-value` 的 values 里加：

```yaml
# 文件：ascend/robot/prod/values.yaml
deployments:
  - name: robot-universal-welcome
    env:
      # 可观测静态字段，见 obs-sdk spec/common-fields.md
      - name: OBS_SERVICE
        value: robot-universal-welcome
      - name: OBS_ENV
        value: prod
      - name: OBS_COMMUNITY
        value: ascend
```

参考 PR：[Open-Infra-Ops/helm-chart-value#1501](https://github.com/Open-Infra-Ops/helm-chart-value/pull/1501/changes)——给 `robot-universal-welcome` 的 Ascend / CANN prod 部署注入 `OBS_*`。

#### 2.1.2 上报代码

无论哪种语言，上报都分 4 步：

1. **初始化注册表**（进程启动一次）
2. **注册指标**（进程启动一次）
3. **上报**（业务事件发生时）
4. **暴露 `/metrics`**（挂中间件与路由）

注册指标时遵守：

- **名称**：`<service>_<name>_<unit>`，全小写 `snake_case`。
  **传基础名，不带 `_total` / `_seconds`**——Go / Python / Java 的底层库自动补后缀；
  **Node 例外**：prom-client 要最终名，SDK 不改名，得自己写 `pr_handled_total`。
- **类型**：动作计数用 Counter（必须带 `result` 维度）、积压/余量用 Gauge、延迟用 Histogram。
- **label 只放低基数枚举**（`result` / `action` / `kind`）。**禁止** `request_id` / `trace_id` / `span_id` / PR number / commit sha —— 每个不同取值都是一条新时间序列，直接撑爆基数。
- 通用 label（`service` / `env` / `instance` / `community`）由 SDK 自动附加，**不要手写**。

**Go**

```go
import (
    "net/http"

    obsmetrics "github.com/opensourceways/obs-sdk/go/metrics"
    obshttpmw "github.com/opensourceways/obs-sdk/go/middleware"
)

// 1. 初始化注册表（启动一次）
m := obsmetrics.New(obsmetrics.Config{})   // 也可显式传 Service / Env / Instance / Community

// 2. 注册指标（启动一次）
handled := m.NewCounterVec("pr_handled", "处理的 PR 事件数", "action", "result")

// 3. 上报（事件发生时）
handled.Inc("opened", "ok")

// 4. 暴露 /metrics（net/http；gin 用 ginmw.Middleware，beego v2 用 InsertFilterChain）
h := obshttpmw.New(obshttpmw.Options{Metrics: m, ResolveCommunity: resolver}).Then(myHandler)
http.Handle("/metrics", m.Handler())
```

参考 PR：[opensourceways/robot-universal-welcome#86](https://github.com/opensourceways/robot-universal-welcome/pull/86)——接入指标并暴露 `/metrics`。

**Python**

```python
from fastapi import Response
from obs_sdk import metrics
from obs_sdk.middleware import fastapi_wrap   # Flask: flask_middleware；Django: DjangoMiddleware

# 1. 初始化注册表（启动一次）
metrics.init()   # 或 metrics.init(service="review", community="openEuler")

# 2. 注册指标（启动一次）
handled = metrics.counter("pr_handled", "处理的 PR 事件数", ["action", "result"])

# 3. 上报（事件发生时）
handled.inc(1, action="opened", result="ok")

# 4. 暴露 /metrics
fastapi_wrap(app, resolver=resolve_community)

@app.get("/metrics")
def metrics_view():
    return Response(content=metrics.generate_text(), media_type=metrics.content_type())
```

参考 PR：[opensourceways/forum-reply-robot#189](https://github.com/opensourceways/forum-reply-robot/pull/189)——接入 obs-sdk-python 统一指标。

**Node**

```js
const obs = require('obs-sdk-node');
const { makeMiddleware, metricsRouteHandler } = obs.middleware;

// 1. 初始化注册表（启动一次）
const m = new obs.metrics.Metrics({ service: 'review' });   // 其余取自 OBS_*

// 2. 注册指标（启动一次；prom-client 要最终名）
const handled = m.counter('pr_handled_total', '处理的 PR 事件数', ['action', 'result']);

// 3. 上报（事件发生时）
handled.inc(1, { action: 'opened', result: 'ok' });

// 4. 暴露 /metrics
app.use(makeMiddleware({ metrics: m, resolveCommunity: resolver }));
app.get('/metrics', metricsRouteHandler(m));
```

**Java**

```java
import io.opensourceways.obssdk.ObsMetrics;
import io.opensourceways.obssdk.ObsSdkConfig;
import io.micrometer.core.instrument.MeterRegistry;
import org.springframework.context.annotation.Bean;
```

### 2.2 日志接入

日志与指标共用同一套部署级字段；代码侧只做初始化、输出、附加上下文三件事，落到 stdout 后由平台采集。

#### 2.2.1 配置环境变量

与 [2.1.1](#211-配置环境变量) **完全相同**：`OBS_SERVICE` / `OBS_ENV` / `OBS_INSTANCE` / `OBS_COMMUNITY`
四个字段三级解析（显式参数 > 环境变量 > 缺省值），且恒非空。同一份 values 的 `env` 同时供日志与指标使用，
不需要配两遍。

#### 2.2.2 日志代码

无论哪种语言，日志接入都分 4 步：

1. **初始化**（进程启动一次）
2. **输出日志**（业务事件发生时）
3. **附加请求上下文**（可选）
4. **写 stdout**（交给 log-agent 采集）

输出日志时遵守：

- **`msg` 是常量短语**：**禁止 printf**（`"failed for user %s"`）。可变数据一律走 kv，否则每行 `msg`
  都不同，LTS 无法按 `msg` 聚合计数，告警规则静默失效。
- **业务字段平铺**：键名小写 `snake_case`，优先平铺、不嵌套。
- **错误走 `error` 字段**：不要把 err 拼进 `msg`。Go 输出 `err.Error()`；Python 等可含完整 traceback
  （仍是单行 JSON）。
- **`trace_id` / `span_id` 是预留位**：有值才输出。首期**不要自己生成**，二期 trace 接入后自动可见。

**Go**

```go
import (
    obslog "github.com/opensourceways/obs-sdk/go/log"
    "github.com/opensourceways/obs-sdk/go/sdkctx"
)

// 1. 初始化（启动一次）
obslog.Init(obslog.Config{Service: "welcome"})

// 2. 输出日志（事件发生时）：msg 常量 + kv 交替
obslog.Info("job done", "event", "release", "issue", "2061")
obslog.ErrorContext(ctx, "get account failed", "user_id", uid, "error", err)

// 3. 附加请求上下文（可选）：request_id / community 由中间件或可信判定点写入
ctx = sdkctx.WithRequestID(ctx, "req-123")
ctx = sdkctx.WithCommunity(ctx, "openEuler")

// 4. 写 stdout：SDK 默认输出，由 log-agent 采集，无需额外代码
```

参考 PR：[opensourceways/robot-universal-welcome#85](https://github.com/opensourceways/robot-universal-welcome/pull/85)——接入 obs-sdk 结构化日志。

**Python**

```python
from obs_sdk import log, _context

# 1. 初始化（启动一次，进程内幂等）
log.init(service="welcome")

# 2. 输出日志（事件发生时）：msg 常量 + 业务字段走 extra
logger = log.get_logger(__name__)
logger.info("job done", extra={"event": "release", "issue": "2061"})

# 3. 附加请求上下文（可选）
with _context.bind(request_id="req-123", community="openEuler"):
    logger.info("handle request")

# 4. 写 stdout：SDK 默认输出，由 log-agent 采集
```

参考 PR：[opensourceways/forum-reply-robot#192](https://github.com/opensourceways/forum-reply-robot/pull/192)——接入 obs-sdk-python 结构化日志。

**Node**

```js
const obs = require('obs-sdk-node');

// 1. 初始化（启动一次）
obs.log.init({ service: 'welcome' });

// 2. 输出日志（事件发生时）：msg 常量 + 业务字段对象
obs.log.info('job done', { event: 'release', issue: '2061' });

// 3. 附加请求上下文（可选）
obs.context.bindRequest({ requestId: 'req-123', community: 'openEuler' }, () => {
  obs.log.info('handle request');
});

// 4. 写 stdout：SDK 默认输出，由 log-agent 采集
```

暂无自研服务的示例 PR：唯一的 Node 项目 Etherpad 属上游开源，接入方式见第 3 章「开源软件接入」。

**Java**

```java
import io.opensourceways.obssdk.ObsSdkConfig;
import io.opensourceways.obssdk.context.RequestContext;
import io.opensourceways.obssdk.log.ObsLogging;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

// 1. 初始化（启动一次）
ObsSdkConfig cfg = ObsSdkConfig.fromEnvironment();
ObsLogging.init(cfg);

// 2. 输出日志（事件发生时）：SLF4J，请求级字段来自 MDC
Logger log = LoggerFactory.getLogger(MyService.class);
log.info("job done");

// 3. 附加请求上下文（可选）
try (RequestContext.Scope scope = RequestContext.push("openEuler", "req-123", null)) {
    log.info("handle request");
}

// 4. 写 stdout：logback-json.xml 的 ConsoleAppender（target: System.out）
```

参考 PR：[opensourceways/openeuler-easysearch#15](https://github.com/opensourceways/openeuler-easysearch/pull/15)——接入结构化 JSON 日志。

Java 的业务字段需在 `logback-json.xml` 的 provider 列表里追加
`<mdc><includeMdcKeyName>tenant_id</includeMdcKeyName></mdc>`，或 SLF4J 2 的结构化 API
`log.atInfo().addKeyValue("tenant_id", id)` + `<keyValuePairs/>`。

> **Java 必须用 SDK 提供的样例配置**：[java/examples/logback-json.xml](../java/examples/logback-json.xml)。
> 它只挂 SDK 的 `ObsJsonProvider`，由 SDK 保证字段名、顺序、毫秒 UTC 时间、小写级别与异常堆栈。
> **不要退回 encoder 自带 provider**：`<logLevel/>` 只能输出大写、字段名不可配，且不配 `<stackTrace/>`
> 时 throwable 会被整条丢弃。

> 服务侧**只写 stdout，一行一个 JSON**：log-agent（fluent-bit，`allContainers: true`）全量采集。

## 3. 开源软件接入

代码不是我们维护的，但有独立用户入口或对外服务——Discourse、Etherpad、Mailman、FreshRSS、LightRAG、PDFMathTranslate、MirrorManager2、mirrorbits、mirrorlist-server、Xihe Gitea、oauth2-proxy、trivy、secrets-manager、COPR、fscrawler。

这条路线**不改代码、不写自研 instrumentation**。按下面的顺序选手段，能停在第一步就不要往下走：

```text
有原生 /metrics？ ──是──> 直接抓（3.1.1 确认、3.1.2 自动发现）
        │否
        ↓
有官方 exporter / 官方插件？ ──是──> sidecar 或独立 Deployment（3.1.3 ②）
        │否
        ↓
需要知道“能不能用”？ ──是──> 黑盒拨测（3.1.3 ③）
需要知道“内部发生了什么”？ ──是──> 日志解析（3.2）
```


### 3.1 指标接入

#### 3.1.1 先确认有没有原生指标

接入前由**服务 owner 确认**：是否暴露 `/metrics`、端口与路径、是否默认开启。下表是常见情况的参考，**以 owner 的确认结果为准**：

| 服务 | 原生指标 | 说明 |
| --- | --- | --- |
| oauth2-proxy | ⚠️ | 支持，但**默认不开启**，需显式设置 `--metrics-address=:44180`；当前部署未配置 |
| Gitea / Xihe Gitea | ✅ | `[metrics] ENABLED = true`，路径 `/metrics`；Xihe fork 需确认是否开启 |
| ingress-nginx、cert-manager | ✅ | 平台组件，已有采集 |
| Discourse | ⚠️ | 需官方插件 `discourse-prometheus`；没装就没有 |
| trivy | ⚠️ | `trivy-operator` 有指标，CLI / Job 形态没有 |
| Etherpad、Mailman、FreshRSS、LightRAG、PDFMathTranslate | ❌ | 无原生 Prometheus 指标 |
| MirrorManager2、mirrorbits、mirrorlist-server | ❌ | 默认无，接入前再确认一次 |
| secrets-manager、COPR、fscrawler | ❌ | 无原生指标 |

#### 3.1.2 采集落点：业务侧与 CI 侧分开

业务/开源软件和 CI 执行资源是**两套独立的采集栈**，配置不能互相写：

| 侧 | 配置位置 | 发现方式 | 写入中心 |
| --- | --- | --- | --- |
| 业务 / 开源软件 | `opensourceways/infra-common` → `common-applications/<cluster>/monitor-agent/prometheus.yml` | `kubernetes_sd_configs`（endpoints）自动发现 | `https://monitoring.osinfra.cn/api/v1/write` |
| CI 执行资源 | `opensourceways/ascend-ci-deployment` → `monitoring/config-for-<cluster>/prometheus-agent-configmap-patch.yaml` | 静态 target | `http://113.44.182.82:9090/api/v1/write` |

平台侧（`infra-common`）已有一条通用 `services` job，**默认不需要为单个服务写 scrape 配置**。关键语法只有三处：

```yaml
- job_name: services
  honor_labels: true
  kubernetes_sd_configs:
    - role: endpoints
  tls_config:
    insecure_skip_verify: true      # 按 PodIP 抓，证书主机名必然对不上
  relabel_configs:
    - source_labels: [__meta_kubernetes_endpoint_port_name]
      regex: http-?port|http|srv|tls-1|ether-http
      action: keep                  # 1. 端口名白名单
    - source_labels: [__meta_kubernetes_namespace]
      regex: monitoring|kube-system|kube-public|kube-node-lease|dapr-system|vault|ingress-nginx
      action: drop                  # 2. 排除系统命名空间
    - source_labels: [__meta_kubernetes_service_annotation_prometheus_io_scheme]
      regex: (https?)
      target_label: __scheme__      # 3. 协议由 Service 注解声明
```

接入方只需满足两条：

- Service 端口名命中 `keep` 正则，否则不会产生 target；
- 端口是 HTTPS 时，Service 加 `prometheus.io/scheme: https`（[infra-common#4284](https://github.com/opensourceways/infra-common/pull/4284)）；不写注解保持 http。

> `role: endpoints` 会按 Pod 展开 target：多副本就是多条 series（带不同 `pod`），**不需要额外做 headless Service**，也不会因 ClusterIP 轮询导致计数器串值。exporter 自带的 label 先确认一下，别和 `service` / `instance` 撞名。

#### 3.1.3 三种接入方式

**① 原生 `/metrics`**

Service 端口名命中白名单即可，无需写 job。以 oauth2-proxy 为例：先在部署参数里加 `--metrics-address=:44180`（默认不开启），再把 Service 的 metrics 端口命名为 `http`（或 `srv`），Agent 会自动发现。

**② 官方 exporter / sidecar**

- sidecar 与主容器共享网络，抓 `127.0.0.1:<exporter-port>`；
- 独立 exporter 用 Service DNS；
- **exporter 的 Service 端口名同样要命中白名单**，否则自动发现不到；
- 典型：`nginx-prometheus-exporter`、服务依赖的 `postgres_exporter` / `redis_exporter`。

**③ 黑盒拨测（没有指标时的最低保障）**

业务集群目前没有现成的拨测框架，可沿用 CI 侧的做法：CronJob 定时探测 → 结果推 Pushgateway → Agent 增加一个 `probe` job 抓 Pushgateway。

统一指标名：

| 指标 | 类型 | 含义 |
| --- | --- | --- |
| `oss_probe_success{service,target}` | Gauge | 1 成功 / 0 失败 |
| `oss_probe_duration_seconds{service,target}` | Gauge | 响应耗时 |
| `oss_tls_expiry_days{service,target}` | Gauge | 证书剩余天数 |

探测内容至少覆盖：HTTP 状态码、响应时间、TLS 证书剩余天数、关键页面内容校验。

### 3.2 日志接入

#### 3.2.1 采集链路

应用写 stdout / 容器日志文件 → log-agent（fluent-bit，`allContainers: true`）→ LTS。开源软件不需要改代码，重点在**采集侧解析**。

#### 3.2.2 三种解析策略

| 日志形态 | 做法 | 适用 |
| --- | --- | --- |
| 结构化 JSON | 直接按字段查询、聚合 | 少数自带 JSON 日志的服务 |

## 4. CI 执行资源

| 形态 | 典型 | 接入动作 |
| --- | --- | --- |

### 4.1 通用骨架

这一段只讲**采集侧**：指标由组件原生提供、还是来自 sidecar / 独立 exporter，都不影响 job 的写法——
只要有一个可抓的 `<地址>:<端口>/metrics`。以 squid（sidecar 形态）为例，配置在
`opensourceways/ascend-ci-deployment` → `monitoring/config-for-guiyang-006/prometheus-agent-configmap-patch.yaml`：

```yaml
- job_name: squid
  static_configs:
    - targets:
        - squid-cache-0.squid-cache-headless.squid:9301
        - squid-cache-1.squid-cache-headless.squid:9301
      labels:
        cluster: guiyang-006
```

四条约定：

1. **`cluster` label 必填**，取值与目录名一致（`config-for-guiyang-006` → `guiyang-006`）；中心所有查询按它筛。
2. **多副本逐 Pod 列出，或用 `role: pod` 动态发现**，不要写 ClusterIP Service——kube-proxy 轮询会让同一副本的
   计数器先在 A 上、后在 B 上，`rate()` 直接算出负值。
3. **`metric_relabel_configs` 只留组件自己的前缀**（`keep` 正则），exporter 附带的大量 Go 运行时指标不值得推。
4. **只在部署了该组件的集群加 target**。这份配置逐集群独立，没有中心统一层。

## 5. CI workflow

### 5.1 指标接入

本节是方案，尚未落地（当前 CI workflow 只有 runner 维度的在跑信息，见[CI 可观测现状 第 8 章](CI可观测现状.md)）。

#### 5.1.1 为什么结果必须从 GitHub 取

现在能拿到的东西都回答不了「这次 workflow 成功了没有」：

1. **`ci_runner_job`** 是 Pushgateway 上的 info 型指标，runner 一结束就被下一次 push 全量替换掉——它只描述"此刻谁在跑"，不留下任何结果。
2. **pod-history-api** 有 `status`（`released` / `rejected` / `expired`）、`duration`、`wait_duration`，但那是 **Pod 生命周期**，不是 job 结论：runner Pod 正常退出不代表 job 成功；而且它只有查询 API，没有 Prometheus 指标。
3. **定制 ARC 的 `EphemeralRunner.status`** 有 `jobRepositoryName` / `workflowRunId` / `jobWorkflowRef` / `jobDisplayName`，**没有 conclusion**——controller 不关心 job 成功与否。

结论只在 GitHub 侧：`run` 和 `job` 都有 `conclusion` 字段。所以结果观测的源是 GitHub Actions API（或 webhook），集群侧数据只做补充。

**触发方式选的是轮询，不是 webhook。** 轮询幂等、能回填历史、不怕丢事件，配额也可控（见 5.1.2）。
代价是延迟。按一次 run 结束起算，端到端是四段叠起来的：

| 阶段 | 最坏 | 中位 | 说明 |
| --- | --- | --- | --- |
| exporter 下一次轮询 | 60s | 30s | 轮询间隔 60s，均匀分布 |
| Prometheus 抓取 | 60s | 30s | 中心集群 `scrapeInterval: 60s` |
| 规则评估 | 60s | 30s | 未配 `evaluationInterval`，取 Prometheus 默认 1m |
| `group_wait` | 10s | 10s | Alertmanager 配置 |
| **合计** | **~3.2 min** | **~1.6 min** | 不含 `for:`（当前规则没写） |

若为了抑制抖动给规则加 `for: 10m`，则变成 12–13 分钟——这 10 分钟是**确认期**，不是轮询造成的。

四段里只有第一段是「在等一个事件」，能被事件驱动替掉；后三段都不认事件：

| 阶段 | 事件驱动能消吗 | 手段与代价 |
| --- | --- | --- |
| 轮询 60s | ✅ 能降到秒级 | 用 GitHub webhook 或 K8s watch（`EphemeralRunner` / runner Pod 终态）作**触发**，事件到了立刻查一次该 run |
| 抓取 60s | ❌ | 只能改 `scrapeInterval`（降到 15–30s，抓取量 ×2~4），或让 exporter 主动 remote-write（丢掉 `up` 与抓取模型） |
| 规则评估 60s | ❌ | 只能调 `evaluationInterval`（全局，所有规则一起变快也一起变重）；Prometheus 没有「数据到达即评估」的钩子 |
| `group_wait` 10s | ❌ | 方向相反，它在故意聚合；设 0 只会把同批告警拆成多封邮件 |

**推荐路径**：事件只作触发、不作数据源——结论仍然逐条问 GitHub（每个 run 一次，比每 60s 扫 21 个仓库更省额度），
60s 轮询保留做对账：事件丢了、或 Pod 已终止但 GitHub 还没写完 conclusion，都要靠它兜。
再配上抓取与评估各降到 30s，告警端到端可到 **1 分钟上下**；要再快只能绕过 Alertmanager 直发通知，
会丢掉分组、静默、去重，一期不做。

**为什么不用 webhook 直接取数**：`workflow_run` 的 `completed` 事件确实秒级，但要在公网提供带 TLS 与签名校验的接收端，
事件丢了只能靠 GitHub 的 redelivery 手工补——对这个场景收益不值。以后若要做「失败即刻通知 PR 作者」，
再上 webhook 做实时触发，轮询继续留在原地做对账。

#### 5.1.2 数据来源

只读 GitHub Actions REST API，不动仓库、不装 App 到 workflow：

| 端点 | 取什么 | 频率 |
| --- | --- | --- |
| `/repos/{owner}/{repo}/actions/runs?status=completed&per_page=100` | 已结束的 run：`id`、`name`、`conclusion`、`run_attempt`、`run_started_at`、`updated_at`、`event` | 60s |
| `/repos/{owner}/{repo}/actions/runs/{run_id}/jobs?per_page=100` | 该 run 下每个 job：`name`、`conclusion`、`started_at`、`completed_at`、`labels`、`runner_name` | 只对新增的 run |
| `/repos/{owner}/{repo}/actions/runs?status=in_progress` | 当前在跑的 run 数 | 60s |

五条约定：

1. **认证用 GitHub App 或服务账号的 fine-grained PAT**，权限只要 `Actions: read` + `Metadata: read`；token 进 Secret，不进配置文件。401/403 必须单独告警——它会让采集**静默归零**。
   当前 21 个仓库分属 **12 个 owner**（含个人仓库 `hiyouga/LlamaFactory`）：fine-grained PAT 只覆盖 token 所有者有权限的仓库，
   跨 owner 要么用 GitHub App 逐个 org 安装，要么用有全量权限的服务账号，别指望一个 PAT 通吃。
2. **去重键是 `(run_id, run_attempt)` 而不是 `run_id`**：re-run 会让 `run_attempt` 递增，只按 `run_id` 去重会把重跑的结果丢掉。具体机制见下面「跨窗口去重」。
3. 每个仓库独立超时，**单仓失败不能拖垮整轮**，失败时保留上一轮的值。
4. **算清速率预算**：认证后 5,000 次/小时。按当前规模（**11 个集群 / 21 个仓库 / 279 个 runner label**，
   见 `ascend-gha-runners` 的 Cluster Map，按 ArgoCD 配置自动生成）：21 个仓库 × 60 轮 = **1,260 次/小时**拉 run 列表；
   新增 run 的 jobs 调用按天算只有几百次，可忽略。`in_progress` 那条不参与失败率计算，放宽到 5 分钟一轮（252 次/小时），
   合计约 1,500 次/小时，占额度 30%。仓库数涨到 60 以上再放宽周期或按仓库分片。
   首屏 100 条要确认够不够——单仓每分钟超过 100 个 run 才需要翻页。
5. **首次启动只建基线**：`last_success_timestamp` 用现有历史回填，否则上线当天满屏"24 小时无成功"。

仓库清单不用手工维护：从中心 Prometheus 查 `count by (repo) (ci_runner_job)` 取近 7 天出现过的仓库，每日生成一次配置。
上线前用 `ascend-gha-runners` 的 Cluster Map 对一遍——那是按 ArgoCD 配置自动生成的，比指标更全
（当前 21 个仓库，其中 9 个跨多个集群，`vllm-project/vllm-ascend` 一个仓库就跑在 6 个集群上）。

#### 跨窗口去重

同一条已结束的 run 会在连续多轮轮询里反复出现在第一页，这是正常的——列表按 `created_at` 倒序，
一条 run 要过一段时间才会掉出首页。去重必须做在 exporter 内部，PromQL 侧补不回来：
同一结论被 `+1` 两次，失败率只会被放大，而且看不出异常。

- **不能用单条水位线 `max(run_id)` 推进**。`run_id` 随创建时间递增，但**完成顺序和创建顺序不一致**：
  一个创建早、跑了 40 分钟的长任务完成时，水位线早已被后创建的短 run 越过去了，它会被永久跳过。
- **用「已计数集合」**：每个仓库维护 `{ "<run_id>:<run_attempt>": <created_at> }`。每轮拉第一页（100 条），
  对 `status=completed` 且键不在集合里的条目各 `+1`，并把键写进集合。同一条 run 被拉到 10 轮也只加 1 次。
- **按首屏边界剪枝**：记本轮首屏最老条目的 `created_at` 为 `horizon`，集合里 `created_at < horizon` 的键直接删。
  列表稳定按创建时间倒序，掉出首页的 run 不会再回来，所以剪完既不会重复计数，集合也不会无限增长（每仓 ≤ 100 条）。
- **状态落盘**：集合与 `last_success_timestamp` 写到 PVC 上的 JSON 文件。进程重启后**把当前首屏整体当基线写入、不回填**——
  宁可缺最前面那几十秒，也不要重复计数；计数器归零交给 `rate()`。
- **已知边界**：① re-run 只在原 run 仍处首屏范围内时才看得到，更早的 run 重跑后到不了第一页；
  ② 单仓一个轮询周期内新增超过 100 个 run 需要翻页（当前 21 个仓库远达不到，翻页逻辑先把接口留出来）；
  ③ **只能单副本**——多副本各自维护集合，必然重复计数。

#### 5.1.3 指标设计

| 指标 | 类型 | 标签 | 用途 |
| --- | --- | --- | --- |
| `ci_workflow_run_result_total` | counter | `repo`、`workflow`、`conclusion`、`event`、`cluster` | 失败率主指标 |
| `ci_workflow_job_result_total` | counter | `repo`、`workflow`、`job`、`conclusion` | 定位是哪个 job 挂了 |
| `ci_workflow_run_duration_seconds` | histogram | `repo`、`workflow`、`conclusion` | 时长分布与变慢趋势 |
| `ci_workflow_consecutive_failures` | gauge | `repo`、`workflow` | 连续失败告警 |
| `ci_workflow_last_success_timestamp_seconds` | gauge | `repo`、`workflow` | "多久没成功过" |
| `ci_workflow_runs_in_progress` | gauge | `repo` | 大盘 |
| `ci_workflow_last_sync_timestamp_seconds` / `ci_workflow_api_errors_total` / `ci_workflow_rate_limit_remaining` | gauge / counter / gauge | — | 自监控 |

表里的 `workflow` 和 `job` 是 GitHub Actions 的两层对象，**都不是 id，也都不是文件名**：

| GitHub 对象 | 是什么 | 标识 | 本方案 |
| --- | --- | --- | --- |
| 工作流 workflow | `.github/workflows/*.yaml` 一个文件；一次运行里的 `run.name` 取文件里的 `name:`（如 `CI`），文件没写 `name:` 时 GitHub 回退成文件路径 | 仓库内唯一；`workflow_id` 是数值 id | `workflow` 标签取 `run.name` |
| 运行 run | 工作流的一次执行（push / PR / 定时触发） | `run_id` + `run_attempt` | **只做水位线与去重，不做标签** |
| 作业 job | YAML 里 `jobs:` 下的一个条目，最终落到某个 runner 上执行 | `job_id`，只在本次 run 内唯一 | `job` 标签取 `job.name` |

三个坑：

- **`workflow` 不是文件名**：标签取 `name:` 而不是 `path`。`name:` 改了、或被删掉回退成路径，都会换一个 series，历史曲线断开——改名时要在变更记录里写一句。
- **矩阵 job 会展开**：`strategy.matrix` 的 job 会变成多个 `job.name` 带参数后缀（`build (aarch64, py3.10)`）。默认保留全名；
  只有某个矩阵维度取值很多（>10）时，才在第一个 `(` 处截断成 `build`，代价是分不清具体矩阵项。
- **`job_id` / `run_id` 禁止做标签**：数值 id 每次运行都变，等于一次运行一个 series，直接撑爆时序。

标签纪律：

- `repo` 用 `owner/name`；`workflow` 用 run 的 `name`（人可读），不要用 `.github/workflows/xxx.yaml` 路径——路径会因为改文件名而换一个 series。
- `conclusion` 归一成小写：`success` / `failure` / `cancelled` / `skipped` / `timed_out` / `action_required`。
  **`cancelled`（人取消）和 `skipped` 不算失败**，混进失败率会长期误报——与 6.1.3 是同一口径。
- `cluster` 从 job 的 `labels` 里匹配 scale set 名反查（如 `linux-aarch64-a3-2-gy004` → `guiyang-004`），**匹配不到就留空，不允许猜**。
- **禁止把 `run_id` / `head_sha` 做成标签**，高基数会撑爆时序。需要定位单次运行的点进去看 GitHub，或用 `run_id` 去和 `ci_runner_job` 在 Grafana 里关联。

#### 5.1.4 告警规则

| 名称 | 条件 | 级别 | 时延 |
| --- | --- | --- | --- |
| `CIWorkflowBulkFailure` | 10 分钟失败率 > 30% 且样本 ≥ 20 | critical | ~3 min（另需窗口内攒够 20 个样本） |
| `CIWorkflowFailing` | `consecutive_failures >= 5` | warning | 取决于运行频次（5 次连续失败）+ ~3 min |
| `CIWorkflowNoSuccess` | `time() - last_success_timestamp > 86400` | warning | 1 天 + ~3 min |
| `CIWorkflowExporterStale` | 距上次成功同步 > 5 分钟，或 `up == 0` | critical | ~7 min（5 min 判定 + 抓取与评估） |

```promql
# 批量失败：分母是全部结论，不是只有成功和失败两种
sum(increase(ci_workflow_run_result_total{conclusion="failure"}[10m]))
  /
sum(increase(ci_workflow_run_result_total[10m])) > 0.3
and
sum(increase(ci_workflow_run_result_total[10m])) >= 20
```

三条注意：

1. **样本量下限（≥ 20）不能省**：夜间只有零星几次运行，挂 1 次就是 50%。
2. 单次失败**故意不告警**，只认"批量"和"连续"，否则正常偶发失败会淹没通知。
3. `CIWorkflowNoSuccess` 要**排除低频仓库**（白名单或"近 7 天运行数 ≥ N"才纳入），否则一周跑一次的仓库会天天报。

结果指标真正的价值是**区分责任边界**，判读规则（不是告警）：

- 同一时间段**多个仓库一起失败**，且 `github_probe_success == 0` → 我方链路问题（DNS / 代理 / 白名单 / 限流）；
- **只有单个仓库失败** → 该仓库代码或 workflow 自身问题；
- **多个仓库同一 job 名失败** → runner 镜像或共享缓存的问题，去看 `runner_version_update_available` 与缓存组件。

#### 5.1.5 部署与运维

- **形态用 Deployment，不用 CronJob + Pushgateway**：Pushgateway 本身能存 counter，问题出在推送方——
  CronJob 是短生命周期进程，计数器每轮从 0 开始，推上去的值反复归零，`increase()` 只会看到重置。
  要用就得自己持久化累计值，另外还要处理 Pushgateway 不做 TTL（进程停了指标停在最后一个值，
  现有探针靠 `push_time_seconds` + `*ProbeStale` 兜底）和多副本写同一个 group 互相覆盖。
  Deployment 单副本暴露 `/metrics:8080` 由中心 Prometheus 抓取，这些都由抓取模型天然解决：
  计数器重置 `rate()` 自己认，target 没了看 `up`。
- **状态存 PVC**：已计数集合与每仓 `last_success_timestamp` 落在 `/data/state.json`，PVC 用 ReadWriteOnce、
  `strategy: Recreate`——单副本的前提下，滚动升级不会出现两个 Pod 同时写同一份去重状态。
  这个文件的完整生命周期见 5.1.2「跨窗口去重」。
- **部署位置**：中心集群的监控命名空间，与现有中心 Prometheus 同网段，能出网访问 `api.github.com`；
  走代理的出口要确认代理放行 GitHub API（`github-probe` 的 `path="proxy"` 就是这条链路）。
  **只部署这一份**：结果只存在于 GitHub、与哪个集群执行无关，每集群一份会重复拉同一批 run（API 额度 ×14）
  还要把 token 分发到 14 个集群；`cluster` 标签是从 job 的 `labels` 反查出来的，不依赖部署位置。
  代价是单点——它挂了就全量失明，所以下面的自监控是必需的，不是可选项。
- **与本仓其他数据源的分工**：结果看 GitHub（本章）；排队与调度看 `RunnerPodPendingTooLong`、`ci_runner_active_jobs`；
  Pod 的等待 / 运行时长看 pod-history-api。三者不互相替代。

### 5.2 日志接入

CI workflow 的日志有两条，来源不同，不要混：

- **job 的步骤输出在 GitHub**（`/actions/runs/{run_id}/logs`，打包 zip），不进集群 LTS。GitHub 侧自己有保留期，
  不建议再往 LTS 灌一份——量大、且和 GitHub 的保留策略对不上。
- **集群侧只有 runner Pod 自身的 stdout**（分配 job、拉镜像、连不上 GitHub 等），已经在 LTS 里，
  适合排查"runner 起不来"这类问题，看不到构建过程。

所以 CI workflow 的日志接入**只做到 runner Pod 这一层就够**，构建失败的具体原因回 GitHub 看。

## 6. Jenkins 任务

Jenkins 任务用于执行 src-openeuler 社区的 CI。

### 6.1 指标接入

#### 6.1.1 为什么自研 exporter 而非 Prometheus 插件

采集走**自研 exporter 拉 Jenkins REST API**，不装 Prometheus 插件。三条理由：

1. `openeulerjenkins.osinfra.cn` 是社区共用门禁控制器。插件的采集线程会遍历全部 job × 构建历史，
   job 数上千时可能拖慢控制器——影响面比告警本身大。
2. 插件只有 `job` 一个维度。`community_check_v2` 是**多参数单 job**，所有仓库的失败糊在一起，
   回答不了"多少仓库受影响"，而"确定责任边界"恰恰是复盘里明确要的。
3. 连续失败次数、最近一次成功时间这两条最关键的信号，插件没有原生指标，只能拿 PromQL 近似拼。

代价是多维护一个服务 + 一套 Jenkins 只读凭据，见 6.1.5。

#### 6.1.2 数据来源

只用 Jenkins **只读 REST API**，不写、不改任何 job：

| 端点 | 取什么 | 频率 |
| --- | --- | --- |
| `/job/<name>/api/json?tree=builds[number,result,timestamp,actions[parameters[name,value]]]{0,50}` | 构建结果（按 build number 增量） | 60s |
| `/computer/api/json?tree=computer[displayName,offline,numExecutors,busyExecutors]` | agent 在线 / 执行器占用 | 60s |
| `/queue/api/json?tree=items[task[name],inQueueSince]` | 排队（可选，只看趋势） | 60s |

四条约定：

1. **认证用 API Token，不用账号密码**；权限只给 `Overall/Read` + `Job/Read`，token 走 Secret，不进配置文件。
2. job 清单递归取 folder（`/api/json?tree=jobs[name,url]`，按 `_class` 判断是否 folder）。
   单个 job 的 API 调用要独立超时，**一个 job 失败不能拖垮整轮采集**，失败时保留上一轮的值。
3. **build number 水位线必须持久化**，重启后从上次位置继续；构建被保留策略清理时水位线**只进不退**，
   否则会重复计数。
4. 首次启动、或新 job 出现时**只建基线、不产告警**，避免上线当天满屏"24 小时无成功"。

#### 6.1.3 指标设计

| 指标 | 类型 | 标签 | 用途 |
| --- | --- | --- | --- |
| `jenkins_build_result_total` | counter | `job`、`result` | 失败率主指标 |
| `jenkins_job_consecutive_failures` | gauge | `job` | 连续失败告警 |
| `jenkins_job_last_success_timestamp_seconds` | gauge | `job` | "多久没成功过" |
| `jenkins_build_duration_seconds` | histogram | `job`、`result` | 构建时长分布 |
| `jenkins_node_online` / `jenkins_node_busy_executors` | gauge | — | 大盘 |
| `jenkins_queue_items` | gauge | — | 大盘 |

标签纪律：

- `job` 用 Jenkins 全名（含 folder，如 `Infra/community_check_v2`），查询侧统一用 `job=~"Infra/community_check.*"` 圈门禁。
- `repo` / `sig` **只在能从 build 参数解析出来时才加**，解析不到就留空，不允许猜。
  参数是否被 Jenkins 记录（`actions[parameters]`）因 job 而异，接入前先 `curl` 一个真实 build 确认。
- `result` 归一成小写：`success` / `failure` / `unstable` / `aborted` / `not_built`。
  **`unstable`（用例失败）和 `aborted`（人主动取消）不算门禁失败**，混进失败率会让告警长期误报。
- **禁止把 build number 做成标签**，高基数会撑爆时序。

#### 6.1.4 告警规则

四条，前三条管门禁，第四条管 exporter 自己：

| 名称 | 条件 | 级别 | 时延 |
| --- | --- | --- | --- |
| `JenkinsBulkFailure` | 10 分钟失败率 > 30% 且样本 ≥ 20 | critical | ~15 min |
| `JenkinsJobFailing` | `consecutive_failures >= 5` | warning | ~30 min |
| `JenkinsJobNoSuccess` | `time() - last_success_timestamp > 86400` | warning | 1 天 |
| `JenkinsExporterDown` | `up{job="jenkins-exporter"} == 0` | critical | 5 min |

```promql
# 批量失败：分母是全部结果，不是只有成功和失败两种
sum(increase(jenkins_build_result_total{job=~"Infra/community_check.*",result="failure"}[10m]))
  /
sum(increase(jenkins_build_result_total{job=~"Infra/community_check.*"}[10m])) > 0.3
and
sum(increase(jenkins_build_result_total{job=~"Infra/community_check.*"}[10m])) >= 20
```

三条注意：

1. **样本量下限（≥ 20）不能省**：夜间门禁流量低，10 分钟只有 2 次构建、挂 1 次就是 50%，
   没有下限会天天误报。阈值也不要高于 30%，否则又退化成靠人肉发现。
2. 单次失败**故意不告警**，规则只认"批量"和"连续"，否则正常的偶发失败会淹没通知。
3. `JenkinsExporterDown` 是自研 exporter 相比插件**新增的风险点**：它是独立服务，挂了会
   **静默失去全部结果观测**（而不是像插件那样跟着 Jenkins 一起被发现），必须自己监控自己。

#### 6.1.5 部署与运维

- **部署位置**：与现有中心 Prometheus 同网段、能访问 `openeulerjenkins.osinfra.cn` 的集群。
  注意该域名在部分出口**解析不到**，采集落点要先确认网络权限，否则 exporter 上线即空跑。
- **资源**：内存 100–200 MB，CPU 只在采集瞬间占用；60s 周期下开销可忽略。这是不装插件的主要原因——
  负载完全外置，控制器零负担。
- **配置外置**：job 过滤规则、token（Secret）、采集间隔，不要硬编码。
- **自监控三项**：采集耗时、最后一次成功采集的时间戳、本轮跳过的 job 数。
  前两项任一异常都会让告警**静默失效**，比报警本身更难发现。
- **与 CES 的分工**：CES（SMN 主题 `alarm-openeuler-jenkins-ci`）管"机器不行了"（节点 / 磁盘 / SFS / ELB），
  本章的 exporter 管"构建失败了"，两者不互相替代。

### 6.2 日志接入
