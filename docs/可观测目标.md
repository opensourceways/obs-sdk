## 0. 可观测范围

本文覆盖**微服务**与 **CI** 两块：

| 块 | 取哪一支 | 层 | 围绕什么建四指标 | 说明 |
| --- | --- | --- | --- | --- |
| **微服务**（CLA、机器人等） | 全部业务微服务 | 业务层 | CLA、机器人等微服务 | 资源层（CPU / 内存 / 磁盘 / 网络）复用云上监控插件，不重复建设 |
| **CI · 参与开源** | 只涉及 GitHub Actions CI | 资源层 | squid、buildkit、karmada | 其余触发方式不在范围内 |
| **CI · 参与开源** | 只涉及 GitHub Actions CI | 业务层 | 项目 workflow 执行过程 | — |
| **CI · 主导开源**（Jenkins CI / CodeArts CI） | 仅考虑 Jenkins CI | 业务层 | 项目 workflow 执行过程 | 只做仍在用 Jenkins 做门禁的那部分 |

## 1. 方法论：The Four Golden Signals

出自 Google SRE Book 第 6 章 *Monitoring Distributed Systems*。Google 的建议很直接：

> **如果一个面向用户的系统只能测四个指标，就测这四个。**

它不是一份指标清单，而是**选指标的过滤器**——任何一条候选指标都应当能落进这四类之一；
落不进去的，要么是这四类中某一类的**下钻**，要么就是**自娱自乐的基础设施指标**。

四个信号及其含义：

| 信号 | 一句话 | 简单说明 |
| --- | --- | --- |
| **Latency**（延迟） | 花多久 | 服务一个请求所花的时间；**成功与失败的延迟要分开统计**，看分位数（P50 / P95 / P99）不看平均值 |
| **Traffic**（流量） | 有多少 | 单位时间内的请求 / 事务量；存储类系统看**事务率**，不看原始字节数 |
| **Errors**（错误） | 失败多少 | 失败请求的占比，分**显式**（5xx）、**隐式**（200 但内容错）、**策略性**（自定义口径）三类 |
| **Saturation**（饱和度） | 还剩多少余量 | 最受限资源的紧张程度（CPU / 内存 / I/O / 网络）；「还剩多少」比「用了多少」更有预警价值 |

**对一个系统做可观测，就是基于用户行为、体验对系统做模块划分、流程拆分后，量化这四个指标。**



## 2. 微服务可观测目标

**同一套指标、两个视图**——研发侧看「为什么坏」，用户侧看「哪块坏了」：

| | §2.1 研发侧 · 内部服务大盘 | §2.2 用户侧 · 社区服务状态页 |
| --- | --- | --- |
| **读者** | 运维 / 研发 | 社区用户（主） |
| **回答的问题** | **为什么坏** | **哪块坏了** |
| **维度** | 服务 × 社区 × **日期** | 模块 × 社区 × 日期 |

## 3. CI 可观测目标

CI 可观测目标分三层：**资源层目标**、**业务层目标**，以及**健康度大盘**（本期不做）。

**按模块拆分**：

| 层 | 取值 |
| --- | --- |
| 第一层 | **参与开源** / **主导开源** |
| 参与开源下一层 | **vllm** / **sglang** / **triton** 等 |

**按流程拆分**：一次 CI 作业流经 **调度 → 镜像拉取 → Pod 启动 → 执行** 等阶段。

再按 §1 的四个信号量化。CI 侧的重点：

- **各阶段各分位耗时**（P50 / P95 / P99）——定位「慢在哪一段」；
- **执行阶段的成功率**——CI 的核心结果指标；
- **失败原因归类**——看失败集中在哪一类，而不是逐个 job 去翻。
