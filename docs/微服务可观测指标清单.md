# 微服务可观测指标清单（评审稿）

---

## 1. 指标分层总览

| 层 | 内容 | 由谁产生 | 是否逐服务定制 |
| --- | --- | --- | --- |
| **T0 通用层** | HTTP 请求数 / 延迟 | SDK 中间件自动 | **否**——26 服务统一，定义一次全员获得 |
| **T1 资源层** | CPU / 内存 / 磁盘 / 网络 | 华为云 CCE 云原生监控插件 | **不建设**（G5，复用云上） |
| **T2 业务层** | 服务特有业务动作、积压、周期任务 | 各服务埋点 | **是**——本文 §3 的主要工作 |
| **T3 拨测层** | 端到端可用性、进程存活 | CronJob → Pushgateway | 按模块，**少量**（§4.4） |

**核心判断**：**T0 覆盖"服务健康度"的骨架，一个服务不写任何业务埋点也已经有 QPS / 错误率 / 延迟**。T2 是需要投入的部分，但要**收敛成最小必须集**（§3.1），不追求每个服务一套漂亮指标——否则 26 个服务的工作量与 series 基数都会失控。

## 3. T2 业务层 —— 需要逐个服务确定的部分

### 3.1 最小必须集（全部 26 个服务）

| # | 要求 | 理由 |
| --- | --- | --- |
| B1 | **1 个业务主 Counter，必须带 `result` 维度**（成功 / 失败分离） | |
| B2 | 有异步 / 队列的服务：**1 个积压 Gauge**（队列长度或消费延迟） | 判"卡住"（§3.2 第 3 问） |
| B3 | 有周期任务的服务：**1 个"上次成功执行时间"Gauge** | 判"没跑"，而不是等下次跑才知道 |
| B4 | 有外部依赖的服务：**外部调用 Counter，带 `result`**（**本期不做**） | 外部依赖出问题，一般都会经由 B1 / B2 / B3 体现出来（动作失败、积压、周期任务没跑成），单看 B4 并不比别人更早发现；且逐服务补外部调用会在 26 个服务上严重扩散改造面 |

### 3.2 业务指标的确定方法：四问法

从**服务对外承诺了什么**倒推，而不是从"服务内部有什么函数"倒推。

| # | 问题 | 产出 | 服务的典型形态 |
| --- | --- | --- | --- |
| 1 | 对外提供什么**动作**？ | 动作 Counter，**成功 / 失败分离** | 所有服务 |
| 2 | 依赖什么**外部系统**？ | 依赖调用 Counter（DB / GitHub API / 华为云 API），带 `result` | 所有有外部依赖的服务 |
| 3 | 会不会**积压 / 排队**？ | 队列深度、最老任务年龄 Gauge | 机器人、爬虫、异步消费 |
| 4 | 有没有**周期作业**？ | 上次成功执行时间戳 Gauge | 同步、清理、爬取类 |

> **第 3 问是重点。** ：「贡献者**无法区分**三种可能——机器人挂了、PR 还在排队、还是自己的提交方式有问题」

## 4. 社区服务状态页（G6）

### 4.1 需求基线：直接采用 backlog#668 的验收标准

### 4.2 四层映射：模块 → 组件 → 服务 → 指标

**这是 #668 验收 3 的落地前提，目前任何地方都不存在，需新建。**

```
模块（用户语言：官网 / 论坛 / 评审机器人 …）
  └─ 组件（运维语言：评审机器人 / 账号 / CLA …）
      └─ 服务（26 个仓：review / label / welcome / om-webserver …）
          └─ 指标（Prometheus series：T0 通用层 + T2 业务层）
```

**建议的初始模块表（待社区运营确认，这正是 §6 的待确认项 2）**：

| 模块（用户可理解） | 组件 | 服务 | 社区维度 |
| --- | --- | --- | --- |
| 代码评审 | 评审机器人 | `robot-universal-review` / `-label` / `-welcome` / `-repo-watcher` | 按 `community` 拆分 |
| 账号与登录 | 账号 | `om-webserver`（+ 其上游依赖） | 按 `community` 拆分 |
| 贡献者协议 | CLA | `app-cla-server` | 全局（仅 Infrastructure） |
| 官网 | 门户 | 待补 | — |
| 论坛 | 论坛 | `forum-reply-robot` + 论坛本体（待补） | 按 `community` 拆分 |
| 会议 | 会议 | `meeting-center` / `meeting-platform` / `app-meeting-server` | 按 `community` 拆分 |
| CVE / 安全公告 | — | `cve-sa-backend` / `cve-manager-ng` | — |

> ⚠️ **模块与组件不是同义词**：模块是"用户想干成的一件事"，组件是"提供它的服务集合"。一个模块可含多个组件，一个组件也可被多个模块引用。这张表**需由社区运营/运维出**，SDK 侧只提供"服务 → 指标"的最底层。

### 4.3 状态集与判定口径

#### 4.3.1 状态集（4 态，**「未知」是一等状态**）

| 状态 | 含义 | 判定 |
| --- | --- | --- |
| **正常** | 有数据且指标健康 | 有数据 + 各判据通过 |
| **降级** | 有数据，但相对自身基线劣化 | 触发 L2 / L3 判据 |
| **异常** | 有数据，但端到端不可用 | 触发 L1 判据 |
| **未知** | **无数据**（未接入 / 零 series / 抓取失败） | 数据缺失 |

> 🔴 **「未知」折叠成「正常」是状态页最严重的设计错误。** 把"没有数据"渲染成绿色的「服务正常」，是在**欺骗用户**——比没有状态页更糟，因为状态页被用户当作唯一事实来源，其可用性要求天然高于内部大盘。

#### 4.3.2 判定口径：分层判据，**不用绝对阈值**

**为什么不绝对阈值**：各社区 QPS 相差几个数量级，绝对阈值在低流量社区**永远不触发**、在高流量社区**天天误报**。

| 层 | 判据 | 映射状态 | 数据来源 |
| --- | --- | --- | --- |
| **L1** | 端到端探针失败（或进程不存在） | **异常** | T3 拨测 |
| **L2** | 错误率相对**自身历史基线**显著抬升 | **降级** | T0 `http_server_requests_total` |
| **L3** | 积压超阈值 / 周期作业未按时执行 | **降级** | T2 业务层（B2 / B3） |

> 基线建议取**同一社区该模块过去 N 天的同环比**，而非全局阈值。阈值确定后需与各社区运维对齐（§6 待确认项 4）。

### 4.4 数据来源：自身上报为主，拨测只兜底

**结论：以服务自身上报为主力，拨测仅补自身上报"结构性测不到"的少数场景。**

| 故障形态 | 自身上报 | 拨测 | 采用 |
| --- | --- | --- | --- |
| **积压**（活着但处理不过来） | ✅ **最优**——kafka consumer lag / 队列长度是**直接测量**，能给出"积压多少、积压多久" | 只能间接推断（"用户超时了"） | **自身上报** |
| 外部依赖调用失败 | ✅ 能测（带 `result` 的依赖调用计数） | 冗余 | **自身上报** |
| **进程整个消失** | ❌ 物理上测不到——没进程就没有指标可上报 | ✅ 唯一手段 | **拨测** |
| **上游事件根本没送达**（webhook 丢包 / GitHub App 权限被撤 / 生产者没发） | ❌ 服务**没收到请求**，指标平静如常 | ✅ 模拟真实动作才测得出 | **拨测** |
| **用户到服务那一跳**（DNS / 网关 / 证书 / 防火墙） | ❌ 服务自查一切正常 | ✅ 唯一手段 | **拨测** |

**落地要求**：

1. **不新建拨测体系**——复用设计文档 §3.1 资源块已有的拨测链路（CronJob → Pushgateway → 中心 Prometheus）。该链路原本用于「外部 API 可达性、云账号余额、证书有效期、共享盘」，**现在把"社区关键组件的端到端可用性"补进去**即可。
2. **拨测范围按模块而非按服务**——只覆盖 §4.2 模块表里"用户真的会去点"的那几个动作，**不做全量**。每多一个探针就多一份误报要压、多一套凭证要轮换。
3. **拨测的成本在维护而非技术**。评审时请一并评审"谁维护这些探测脚本"。

### 4.5 每日可用性 → 四档颜色的算法

#668 验收 1 要求"按天 + 不可用时长分 4 档"。需要一个确定的映射：

```
每日可用性 = 1 - (当日"异常"状态的累计分钟数 / 1440)

档位 0   （最深色）：可用性 = 100%（当日无异常）
档位 25            ：不可用 ≤ 25%    （< 6h）
档位 50            ：不可用 ≤ 50%    （6h ~ 12h）
档位 100（最浅色）：不可用 > 50%     （> 12h）
```

算法配套两个口径：

- **「未知」不计入分母**，单独渲染为**灰色空格**，与 4 档颜色互斥——否则"没接入"会被算成"服务很好"。
- **单次故障的起止时间**由 §4.3 的状态机产出（异常 → 恢复），即 #668 验收 2 的「故障发生 / 问题处理 / 问题恢复」三态事件流；"问题处理"态由**人工在状态页登记**（系统无法自动判断），这需要在实现侧预留操作入口。

### 4.6 已知盲区 —— 状态页「未知」态的现实来源

以下盲区**已实测确认**，是状态页"未知"态的现实来源，评审时需接受：

| 盲区 | 实测事实 | 状态页表现 |
| --- | --- | --- |
| `robot-framework-lib` 的 121 处 logrus 打点 | 字段集无 `community` / `service`，在按 community / service 必选筛选的大盘上**不可见** | 未知 |
| **接入覆盖率远低于预期** | openeuler 集群 65 个抓取目标里，**59 个 30 天内从未 up 过**；hpckit 25/32 从未 up。`up == 0` 多数**不是故障，是没暴露 `/metrics`** | 未知（"目标在线率"不是健康度） |
| **空 vec 消失** | `client_golang` 懒初始化：某 vec 无任何数据时，该指标**完全不出现**在 `/metrics` 上（连 HELP / TYPE 行也没有），外观与"该指标从未接入"一致 | 未知 |
| 硬件级 | CPU / 内存 / 磁盘 / 网络由云上提供，**没有 `community` label**，只能按 `cluster` 过滤 | 不纳入状态页 |

## 5. 基数与容量提醒

设计文档 §4.7.2 明确：**series 数是容量规划里唯一的未知量**（中心 Prometheus 一期单机 30d，`replicas: 2` 不是 HA 而是分片）。

估算时须实算：

```
series ≈ Σ(服务 × 指标数 × 业务 label 组合数 × community 数)
```

**基数构成**：

- `community` 是**低基数**（18 个枚举内）；
- `request_id` / `trace_id` / `span_id` / `user_id` / `pr_id` 是**高基数**，进 label 会按取值量级放大 series——这正是「series 数是唯一未知量」的主要来源；
- `path` 取路由模板还是原始 URL、`result` / `status_code` 是否枚举封闭，直接决定 label 组合数；
- Java 走 Actuator 时 `uri` 已由框架做模板化，但自定义业务 label 仍需单独核算。
