# CI 可观测目标：从问题发现到根因分析与故障自愈

本文定义 CI 可观测要达成的目标，以及为达成目标需要建设的能力。具体指标、组件与实现细节见
[可观测接入指南](可观测接入指南.md) 第 5 章，本文只回答三个问题：**目标是什么、路线是否成熟、每一步的前置条件是什么**。

## 1. 目标与边界

### 1.1 三级目标

| 级别 | 要回答的问题 | 验收标准 |
| --- | --- | --- |
| **L1 问题发现** | 哪条流水线、什么时候、失败了还是排队中 | 一次失败在 2 分钟内产生可读告警；排队超阈值在 7 分钟内告警 |
| **L2 根因分析** | 是平台的问题还是代码的问题，卡在哪个环节 | 告警附带「疑似根因 + 证据链接 + 建议动作」，人看一眼能确认 |
| **L3 故障自愈** | 系统能否自己把可恢复的故障修掉 | 高频、确定性的基础设施故障自动恢复，且误判率可控、动作可回滚 |

### 1.2 现状基线

- **一期**（aggregator）：run/job 结果与耗时、在途排队与执行、三条轮询路径、结果级告警。
- **二期**（ghalistener / 集群侧）：容量 gauge、②+③ 启动耗时、④ 执行耗时。
- **三期**（ci-event-agent）：run 身份、重跑补齐、Pod 生命周期事件。

L2 与 L3 都建立在三期之上——**没有 run 身份，根因分析只能到「某个仓的某个 workflow」这一层**。

## 2. 这条路有没有标准

结论：**发现问题有标准可对齐，根因分析和故障自愈没有标准**，只有一条被反复验证的参考架构。选型时不要把「某产品宣称的 AIOps」当成标准。

| 层 | 标准化程度 | 可对齐的锚点 |
| --- | --- | --- |
| L0 数据模型 | 高 | OpenTelemetry **CI/CD 语义约定**（RC）：`cicd.pipeline.run.id` / `.state` / `.result`、`cicd.pipeline.task.run.id`、`cicd.worker.*`；[spec/otlp-mapping.md](spec/otlp-mapping.md) 已有字段映射的先例 |
| L1 检测告警 | 高 | SLI/SLO + burn-rate（Google SRE），symptom-based 而非 cause-based |
| L2 上下文富化 | 中 | OTel k8s 约定（`k8s.pod.name` / `k8s.node.name`）+ 变更事件；拓扑模型无统一标准 |
| L3 根因分析 | 低 | 无标准。共识模式：统一遥测 → 拓扑/依赖关联 → 变更关联 → 假设排序 → 人确认 |
| L4 故障自愈 | 低～中 | 无标准。共识是 K8s operator 控制回路 + 动作白名单 + shadow/审批/熔断 |
| L5 效果评估 | 低 | MTTD / MTTR / 自愈成功率 / 误判率，各家都在用，口径不统一 |

**一条硬约束**：`cicd.pipeline.run.id` 用作 metrics 标签会造成高基数，OTel 语义约定本身就要求必须 opt-in。这与指南 5.4.1「`run_id` / `head_sha` 禁止做标签」一致——**run 身份走日志、事件与 resource attribute，不走指标标签**。

## 3. 参考架构

```
L5 评估         MTTD / MTTR / 自愈成功率 / 误判率 / 重复失败率
                  ▲
L4 自愈         remediation controller：动作白名单 · 三档推进 · 熔断 · 审计
                  ▲
L3 根因         签名匹配 · 阶段定位 · 相关性 · 变更关联 → 「假设 + 证据」
                  ▲
L2 富化         告警附带上下文：run → EphemeralRunner → Pod → 节点 → 卡池 → 变更
                  ▲
L1 检测         SLO / burn-rate：成功率、排队时长 p90、启动耗时 p90
                  ▲
L0 语义         统一身份与字段：run_id / job_id / platform / repo / workflow / branch_class
```

每层只依赖下一层的产出，不能跳层：**没有 L0 的身份，L2 富化拼不出链路；没有 L2 的上下文，L4 的自愈只能靠猜。**

## 4. 建设内容

### 4.1 数据地基（L0）

现有指标能回答「哪个仓、哪个 workflow、失败还是排队」，但回答不了「哪一次 run、哪一个 Pod、哪台节点」。RCA 需要补四类信号：

| 信号 | 内容 | 来源 | 期次 |
| --- | --- | --- | --- |
| **run 身份贯穿** | EphemeralRunner / runner Pod 打上 `run_id`、`job_id`（pod label 或 annotation），让 LTS 里的日志能按 run 检索 | 定制 ARC 写入 + event agent | 三期 |
| **Pod 生命周期** | Pending → Created → Ready → Completed 的时刻与状态，用来拆分 ②扩容 / ③启动 | ci-event-agent watch EphemeralRunner + Pod | 三期 |
| **k8s 事件** | `FailedScheduling` / `FailedMount` / `ErrImagePull` / `OOMKilled` / `Unhealthy` | kube-event exporter | 三期 |
| **变更时间线** | values/chart 版本、runner 版本、节点池扩缩、镜像源切换时刻 | GitOps commit 历史 + 发布记录 | 可提前，成本最低 |

变更时间线是性价比最高的一项：CI 故障的根因里「最近改了什么」占比极高，而部署全在 GitOps 里，接入只是把 commit 时间线拉进查询。

### 4.2 失败分类法（L3 的前提）

没有分类，根因分析就是猜。先定义可判定的类别：

| 类别 | 典型签名 | 可否自愈 | 责任方 |
| --- | --- | --- | --- |
| 资源不足 | Pod Pending、`FailedScheduling`、scale set desired 卡在 0 | ✅ 扩容 / 排空 / 换标签 | 平台 |
| 镜像 / 网络 | `ErrImagePull`、拉 pypi/npm 超时、proxy 5xx | ✅ 切源、预热、重跑 | 平台 |
| 存储 | 共享盘 mount 失败、no space、inode 满 | ✅ 清理 / 迁移 / 重跑 | 平台 |
| runner 生命周期 | listener 失联、注册失败、EphemeralRunner 残留 | ✅ 重建 / 清理 | 平台 |
| 配置 / 配额 | 无匹配 label、并发排队、token 过期 | ⚠️ 半自动，改配置要人批 | 平台 |
| 超时 / 卡死 | job 跑数小时、占卡不用 | ✅ 杀 Pod 释放 | 平台 |
| 外部依赖 | GitHub / GitCode 或公共源不可达 | ⚠️ 重试，不自愈 | 外部 |
| 代码 / 测试 | 编译错误、断言失败、flaky 用例 | ❌ 只归因与通知 | 作者 |

**大部分失败落在最后一行**：vllm-ascend 实测最近 100 个 run 里 86% 由 PR 触发、失败率 14.5%，其中绝大多数是贡献者代码或 flaky 用例。L3 的价值集中在基础设施类——这也是判断投入是否值得的前提。

### 4.3 根因分析（L3）

按性价比排序的三板斧：

1. **阶段定位**：先看卡在 ①平台排队 / ②③启动 / ④执行。①→并发或配额；②③→节点资源、镜像、挂载、网络；④→代码或资源超时。这一步就能砍掉一半排查面。
2. **签名匹配**：从 job 日志抽取错误模板并归类（正则/SQL 聚类），先覆盖高频签名，规则库够到七成即可，剩余再上统计。
3. **相关性归因**：多仓、多 workflow 在同一时间窗同时失败 → 平台侧；单仓单 workflow → 代码或该仓配置。「最近一小时内改过什么」作为最强的佐证。

输出形态固定为「假设 + 证据 + 建议动作」，且证据必须可点开（日志查询、指标快照、变更 commit）。LLM 只用于日志摘要与假设排序，**不做判定**，且结论必须能溯源。

### 4.4 故障自愈（L4）

只做幂等、可回滚、影响面可控的动作：

| 动作 | 触发条件 | 风险 |
| --- | --- | --- |
| 重跑失败 job（限一次） | 签名属于基础设施类，同一 commit 二次重跑 | 低 |
| 清理残留 EphemeralRunner / 卡死 Pod | 已终态但 Pod 残留，或 running 超阈值 | 低 |
| 取消僵尸 run | 本仓、超 7 天仍未启动 | 低（fork run 慎动） |
| 重建失联 listener | 心跳缺失且 scale set 无响应 | 中 |
| 节点池扩容 / 排空坏节点 | Pending 超时且该池无可用卡 | 中 |
| 清理占卡不用的 NPU | 占卡超阈值且无活跃 job | 中 |
| 切换镜像源 / 预热镜像 | 拉取失败签名命中 | 中 |
| 调整并发上限 / 改 scale set values | ❌ 不自动 | 改配置一律走人 |

推进必须分三档，且每档有退出条件：

1. **shadow**：只输出建议，不执行；跑满四周，统计建议被采纳的比例；
2. **approval**：推送到 IM/邮件，一键确认执行；
3. **auto**：仅对通过 shadow 与 approval 验证、误判率低于阈值的动作开放。

护栏（缺一条不上线）：动作幂等 + 冷却期 + 单 run 重跑次数上限；全量审计日志；熔断（自动动作后问题仍存在的比例超阈值即停用该类动作）；主干与发布窗口内不自动执行。

### 4.5 效果评估（L5）

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| MTTD | 故障发生到告警 | ≤ 2 分钟（结果类）/ ≤ 7 分钟（排队类） |
| MTTR | 故障发生到恢复 | 按类别设定，基础设施类 ≤ 30 分钟 |
| 自愈成功率 | 自动动作后问题消失的比例 | 先观察，不设硬指标 |
| 误判率 | 自动动作后问题仍在 / 被人回滚 | < 30%，超阈值熔断 |
| 重复失败率 | 同一签名在同仓反复出现 | 下降趋势，用于验证根因是否真被修掉 |

## 5. 技术选型与借鉴

### 5.1 可直接借鉴

| 方案 | 用在哪一层 | 说明 |
| --- | --- | --- |
| **OTel CI/CD 语义约定** | L0 | 字段命名对齐；成熟度 RC，`run.id` 不进 metric label |
| **Argo Events + Argo Workflows** | L4 | 已在用 ArgoCD，事件驱动自愈编排成本最低，无需引入新运行时 |
| **Kubernetes operator 模式** | L4 | 自研 remediation controller 的骨架，动作白名单、状态机、审计都按 CRD 表达 |
| **cluster-autoscaler / Karpenter** | L4 | 节点池扩缩；runner 扩缩仍由 ARC scale set 负责 |
| **OpenKruise** | L4 | 原地重启、PodProbeMarker，适合安全重启而不是删了重建 |
| **Develocity Build Scans 思路** | L3 | 构建耗时与缓存命中率的回归检测，触发「构建变慢」类告警 |
| **依赖图谱思路（Netflix Astrid）** | L3 | 把源码仓、依赖包、基础镜像、runner 视为有向图，失败时沿依赖回溯 |

### 5.2 谨慎或不用

| 方案 | 问题 |
| --- | --- |
| **Keptn** | 2025 年 9 月已被 CNCF 归档，不再作为选型依据 |
| **StackStorm** | 能力可用，但会多养一个运行时；Argo Events 已能覆盖 |
| **Karmada / Volcano** | 不是 runner 扩缩容工具：Karmada 是多集群分发，Volcano 是批处理调度。runner 扩缩在 ARC scale set + 节点池 |
| **Netflix「Open_CI」** | 查无此项目；Netflix 实际是 Develocity Build Scans、Astrid、Spinnaker Builds。借鉴思想即可，不要引用不存在的项目 |
| **eBPF（OBI / Beyla）** | 能补 DNS 与连接拒绝的证据，但出网问题主要在 squid 与 registry，已有指标覆盖；优先级最低 |
| **商业 AI SRE（Datadog Bits 等）** | 方法论一致（富化后的遥测 + 关联 + 假设排序），差别在数据覆盖而非模型；不引入平台，只借鉴形态 |

## 6. 分期与门槛

| 能力 | 依赖数据 | 期次 | 进入门槛 |
| --- | --- | --- | --- |
| 结果 / 在途检测、失败率与排队告警 | 一期指标 | 一期 | — |
| 变更关联根因（「最近改了什么」） | GitOps 时间线 | 可与二期并行 | 变更覆盖率 ≥ 90% |
| 资源型根因（没卡、池满、节点坏） | 二期 listener 容量指标 | 二期 | 各集群已接入 scrape |
| 精确 RCA（run → Pod → 节点） | run 身份 + Pod 生命周期 + k8s event | 三期 | run 身份覆盖率 ≥ 90% |
| 自愈：重跑 / 清理 / 重建 | 三期事件 + 动作权限 | 三期后段 | shadow 满四周且建议采纳率达标 |
| 自动自愈白名单 | 上述全部 | 四期 | 误判率连续两周低于阈值 |

**三个覆盖率指标**（run 身份、Pod 事件、变更）是判断路线是否走偏的硬指标。任何一项没到约 90%，RCA 与自愈都只能是演示。

## 7. 边界与风险

- **CI 失败的主体是代码与测试**，基础设施类只占少数。目标定的应是「把基础设施类故障的发现与恢复做快」，而不是「让所有失败都能自愈」。
- **自愈可能掩盖故障**：自动重跑会让真实回归变成间歇失败。因此重跑必须限次，且「重跑后仍失败」与「重跑后成功」要分开计数。
- **GitCode 侧能力不完整**：没有 EphemeralRunner 与 ghalistener，L2 之后的分析在一期只能覆盖 GitHub 半边，接入前需实测其 API 能提供的事件粒度。
- **单点与静默失效**：aggregator 单副本、凭据过期会让采集静默归零。自监控告警必须先于 RCA 上线（见指南 5.2.3）。
- **不要先上 LLM**：没有签名库与拓扑关联时，模型只会给出无法验证的解释。

3. 三期 event agent 能否拿到 Pod 创建 / Ready 时刻——这是拆分 ②扩容 / ③启动 的唯一来源。
4. GitCode 侧是否需要独立的失败分类与自愈策略，还是先只做观测。
