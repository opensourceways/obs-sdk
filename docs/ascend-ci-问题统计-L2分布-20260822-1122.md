## 四、口径与方法

### 4.1 分母

| 口径 | 数量 | 说明 |
| --- | ---: | --- |
| 全部问题 | 215 | 复盘总量 |
| 剔除监控/巡检/治理需求 | 212 | 3 条不是故障 |
| 再剔除业务侧 | 185 | 业务侧配置/脚本/用例问题，不是平台故障 |
| 再剔除未定位 | **182** | 本文口径 |
| 其中未定位（单列） | 3 | 信息不足，不混进主导类 |

### 4.2 L2 是怎么归的

1. 解析 HTML 内嵌 `DATA` 数组（215 条），每条有 `sym` / `rc_detail` / `plain`；
2. 按 `stage` 先限定候选范围（例如「日志/结果上传」不参与「计算」类匹配）；
3. 用人工定义的「关键词 → 组件」规则匹配，优先归到最具体的组件；
4. 匹配不到的落到「未细分」桶（调度 8、镜像 6、网络 2 等）；
5. **单标签**：每条记录只归一个 L2，因此各表可以加总到 182。

> 与「提及次数」多标签版本的区别：多标签会一条记录计多次，不能加总；本文用单标签是为了让分布可加总、可占比。

### 4.3 已知局限

- **规则提取，不是人工标注**：CANN、hooks 等组件对规则敏感，换一版规则数量会漂移（实测 CANN 从 18 变到 6）。
- **「未细分」不是没问题**：是记录里没写清具体组件；需要补 `failure_signature` 才能落到组件级。
- **组件级适合排期，链路级适合对外**：链路级排序比组件级更稳。
- 报告头部的部分数字与明细不一致（例如「GitHub 137 / 存量 35」），建议以明细为准修正后再对外引用。
