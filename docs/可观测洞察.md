# 可观测洞察

> 调研时间：2026-10-26。范围：国内外可观测厂商的产品主线与技术路线，以及与本仓库（obs-sdk / 社区可观测 / CI 可观测）的关系。
> 本文是**调研结论**，不是契约；字段与指标定义见 [spec/](../spec/README.md)，建设目标见 [可观测目标.md](可观测目标.md)。

## 0. 结论摘要

1. **采集层已经商品化**。OpenTelemetry 于 2026-05-21 从 CNCF 毕业，traces / logs / metrics 全 GA、Profiles 成为第四信号；厂商竞争整体上移到"数据底座、成本、以及 AI 驱动的分析与处置"。自研采集不再有价值，**语义对齐**才有。
2. **2026 年的主战场是两件事**：Agentic Ops（AI 完成定位与处置）与 AI Agent 自身的可观测（Token、成本、效果）。前者仍在"调查可用、修复受控"的阶段，后者已形成语义约定与产品线。
3. **对我们是利好**：现有的"契约先行 + 薄封装 + 黄金四信号 + 零埋点中间件"路线与行业方向一致；真正要补的只有三件低成本的事——**语义映射、标签纪律、CI 指标的标准命名**。

## 1. 技术趋势

| # | 趋势 | 一句话 | 成熟度 |
| --- | --- | --- | --- |
| 1 | 采集商品化 | OTel 毕业，语义约定成为新的契约层 | 已标准 |
| 2 | 零侵入 | eBPF / OBI 不改代码取指标与链路 | 生产可用 |
| 3 | Agentic Ops | 检测 → 假设 → 验证 → 处置的闭环 | 调查可用，修复受控 |
| 4 | AI Agent 可观测 | Token、成本、工具调用、效果评估 | 快速演进 |
| 5 | 成本治理 | 遥测数据的采样、聚合、分层与计价 | 已成选型首因 |
| 6 | 数据底座 | 存算分离、统一查询、变更观测 | 头部已落地 |

### 1.1 采集层商品化：OTel 毕业，语义约定成为契约层

- OpenTelemetry 2026-05-21 成为 CNCF Graduated 项目，三家信号全部 GA，Profiling 进入规范。
- 语义约定（semantic conventions）实际承担了"跨厂商字段契约"的角色：资源属性（`service.name` / `deployment.environment.name` / `service.instance.id`）、HTTP（`http.server.request.duration`）、异常（`exception.*`）、CI/CD（`cicd.*`，Release Candidate）都已成文。
- `gen_ai.*` 已**迁出主仓**，由独立的 `semantic-conventions-genai` 仓维护（无 tag，按 commit 锚定），说明这一块的变动仍快。

**判断**：采集不是差异化，字段命名才是。字段一旦私有化，换后端、接 AI 工具都要重做。

### 1.2 零侵入：eBPF 走向默认

- Grafana 的 Beyla 已并入 **OpenTelemetry eBPF Instrumentation（OBI）**，通过 hook TLS 读写拿到明文 HTTP，无需改代码即可产出 span；对 LLM 流量还能直接按 GenAI 语义产出。
- 同类：DeepFlow（云杉，AutoMetrics / AutoTracing）、groundcover、Pixie、Cilium Tetragon。
- 国内阿里云已把 OBI 接入做成产品能力。

**判断**：资源层、网络层、框架层的信号会被零侵入方案吃掉；**业务语义**仍然只能靠埋点——这正是本仓库 T0（中间件）+ T2（业务指标）分层的价值所在。

### 1.3 从"看得见"到"能处置"：Agentic Ops

- Datadog Bits 系列（SRE / Investigation / Code / Release / Agent Builder / Agent Evals），Dynatrace Intelligence（确定性 Davis + agentic AI），阿里云 STAROps（数字员工 + MCP），腾讯云 Multi-Agent 可观测工作台，以及 Resolve.ai、Traversal、Cleric 等新贵。
- 共同点：**靠拓扑、变更、历史事件做 ground truth**，靠只读默认、写操作审批、审计日志做 guardrail。

**判断**：AI 诊断的上限由数据质量决定。字段乱、基数爆、缺变更信息，再强的 agent 也只能在噪声里猜。先把数据整理干净，比先买 AI 更有效。

### 1.4 AI Agent 自身成为观测对象

- 新指标层：输入/输出 Token、每任务成本、工具调用链、会话回放、完成率与效果评估。
- 厂商动作：Datadog Agent Console / Tokenomics（跟踪 Claude Code、Cursor 等编码 agent 的用量与花费）、腾讯云 Agent 可观测（2026-09 上线）、博睿 AI 可观测、Dynatrace AI Observability app。
- 工程共识：**评估（evals）与观测共用一个 trace store**，避免"链路在 A、评估在 B"的搬运成本。

**判断**：传统四信号解释不了非确定性的 agent 行为；如果将来要观测自家机器人调用 LLM，需要另起一层语义，而不是硬塞进 HTTP 指标。

### 1.5 成本治理成为一等公民

- Grafana **Adaptive Telemetry** 四信号闭环（Metrics / Logs / Traces / Profiles，Profiles 于 2026-08 GA），用自适应聚合与采样降本；Cribl 专做遥测管道；各家普遍支持尾部采样与分层存储。
- 计价模式在变：从 per-host 转向 per-GB、per-credit、按命名指标数（Datadog Infinite Cardinality）。
- 行业调查中，**成本已超过功能成为选型的首要标准**。

**判断**：厂商的做法本质是"事后补救"——先收全量再压缩。我们的规模下，**从源头控制基数**（高基数不进 label、路由模板、不重复埋点）是同等有效且更便宜的做法。

### 1.6 数据底座：统一查询与变更观测

- Dynatrace Grail、阿里云 UModel、博睿 Titan、观测云 GuanceDB 3.0、Observe 的 S3 湖：方向一致——**存算分离 + 一套查询同时覆盖指标/日志/链路**。
- 新兴信号：**变更**被提升为一级数据（观测云把 Jenkins / GitLab / K8s Events / Nacos 的变更纳入叠加分析与风险评分），因为多数故障由变更触发。

**判断**：我们已有 Prometheus + LTS + Grafana 的组合，底座不必重建；缺的是把"变更"作为维度接进大盘（发布、配置、镜像 tag）。

## 2. 厂商趋势

### 2.1 国际格局：AI 与成本重塑排名

Gartner 2026 年 7 月《可观测平台魔力象限》（19 家）：

| 象限 | 厂商 |
| --- | --- |
| Leader（8） | Chronosphere、Coralogix、Datadog、Dynatrace、Elastic、Grafana Labs、IBM、New Relic |
| Challenger（5） | Alibaba Cloud、AWS、LogicMonitor、Microsoft、Splunk |
| Visionary（2） | BMC Helix、Honeycomb |
| Niche（4） | Apica、HPE、ScienceLogic、SolarWinds |

与 2025 年版（20 家，Leader 为 Chronosphere、Datadog、Dynatrace、Elastic、Grafana Labs、IBM、New Relic、**Splunk**）相比，本轮的净变化只有两处：**Splunk 降至 Challenger；Coralogix 由 Visionary 升入 Leader**。Chronosphere 是**连续第三年** Leader，不是新晋。

报告主题明确指向 AI 工作负载（LLM / agent 观测、agentic AIOps）、遥测成本控制与 OTel 原生摄入，这是 Gartner 与媒体一致的口径。但要注意两点：

- 魔力象限的坐标轴是 **Completeness of Vision × Ability to Execute**，Challenger 的含义是**执行仍强、愿景相对落后**，不等于某项能力（如 AI）弱；
- Gartner 不公开逐家评分与理由。公开材料能证实的只有 **Coralogix 在 Cost Optimization 用例排第 3**；Splunk 下移更可能与 Cisco 体系内的产品整合与路线图清晰度有关（AppDynamics / Splunk Observability / ThousandEyes 存在重叠），而不是 AI 能力——它恰恰是 2026 年 AI 动作最大的一家（AgenticOps、收购 Galileo）。

### 2.2 三条产品路线

| 路线 | 代表 | 优势 | 代价 |
| --- | --- | --- | --- |
| **平台型**（全栈 + AI 编排） | Datadog、Dynatrace、Splunk/Cisco、New Relic、阿里云、腾讯云 | 开箱即用、AI 能力强、体验统一 | 价格高、迁移成本高、数据主权受限 |
| **开源 / OTel-native**（可退出） | Grafana Labs、Honeycomb、Chronosphere、groundcover、SigNoz | 数据可导出、成本可控、无锁定 | 运维成本自担、能力需自行拼装 |
| **遥测管道 / 成本层** | Cribl、Observe | 不换后端即可降本、做脱敏与路由 | 多一层组件、只解决成本不解决分析 |

**判断**：我们走的是第二条路线（Prometheus + Grafana + LTS 自建），退出成本低是结构性优势，应继续守住"数据可导出、字段可映射"。

### 2.3 新贵与并购：能力正被大厂吸收

- **AI SRE**：Resolve.ai（创始团队含 OTel 共同作者，2026 年估值约 15 亿美元）、Traversal（因果 ML、默认只读）、Cleric（只读 + 受控写）等；同时 Azure SRE Agent、AWS DevOps Agent 已内置于云平台。
- **LLM 观测**：Langfuse、LangSmith、Arize（Phoenix / AX）、Braintrust，以及 OpenLLMetry（Traceloop，已被 ServiceNow 收编）。
- **并购**：Cisco 收购 Galileo 补 Agent 观测与 guardrail；Datadog、Dynatrace 持续把 agent 能力并入主平台。

**判断**：单点工具的窗口在收窄，自建 AI 诊断的窗口同样在收窄——这类能力更适合"买/接"，而不是"造"。

### 2.4 国内市场：云厂商一体化 vs 独立厂商 + 信创

| 厂商 | 2026 主线 |
| --- | --- |
| 阿里云 | CMS + SLS + ARMS 合并为**云监控 2.0**，以 UModel 统一模型为底座；**STAROps** 提供数字员工与 SRE Agent；ARMS 的 LLM 监控更名为 **AI Agent 可观测**；已产品化 OBI 接入 |
| 腾讯云 | TCOP 的 Multi-Agent 可观测工作台、SRE Agent、向 L4 无人值守演进；2026-09 上线 **Agent 可观测**（全链路、Token 成本、效果评估）；200+ 云产品 MCP |
| 华为云 | AOM 整合 APM / LTS / CES / Prometheus，AOM 2.0 以应用为中心；**2026 年公开的新能力明显少于阿里/腾讯**，更多是与伙伴联合交付 |
| 火山引擎 | APMPlus 走开放路线，允许第三方探针（如博睿）上报 |
| 博睿数据 | Bonree ONE 4.0：AI 可观测 + Sage AI 运维智能体工作台 + 统一读写引擎；IDC APMO 份额居首 |
| 观测云 | Obsy AI SRE Agent、Blueprint 低代码编排、**变更观测**、GuanceDB 3.0 存算分离 |
| 开源 | DeepFlow（eBPF 零侵入）、夜莺 Nightingale（Prometheus 上层告警）、OpenObserve（S3 低成本日志） |

**判断**：国内厂商在 Agentic Ops 上的宣传比国外更激进，但落地同样受限于数据质量与权限边界；选型时应看"数据能不能导出、字段能不能映射"，而不是看 agent 的演示。

### 2.5 定价与采购关注点

- 计价从 per-host 转向用量型（per-GB / per-credit / 按指标数），因为 autoscaling 让 per-host 失真。
- 采购关注点排序变为：**成本 → OTel / OTLP 兼容 → 可退出性（数据导出）→ AI 能力 → 功能覆盖**。
- 与我们相关的一条：**不要把可观测数据锁进任何不可导出的后端**；LTS、Prometheus 都支持导出，这是我们的优势，也是将来接 OTLP 的后路。

## 3. 自身相关性

### 3.1 已被验证正确的三件事

1. **薄封装、不自研 instrumentation**——采集层已被 OTel / OBI 商品化，自研没有价值；我们只做装配与约定，方向正确。
2. **黄金四信号 + T0 零埋点中间件 + T2 业务指标**——资源层交给官方 instrumentation，业务层才埋点，与行业"零侵入 + 业务语义"的分工一致。
3. **契约先行**——`spec/` 的四语言契约，本质是一份私有语义约定；它让我们可以在不依赖任何厂商的前提下保证跨语言一致。

### 3.2 现在就该做的三件事（低成本、高杠杆）

| 动作 | 产出 | 状态 |
| --- | --- | --- |
| **字段语义映射** | [spec/otlp-mapping.md](../spec/otlp-mapping.md)：落盘字段 → OTel 语义键 | 已完成，PR #40 |
| **标签纪律 = 成本治理** | 继续执行"高基数不进 label、路由模板、不重复埋点"；这是比 Adaptive Metrics 更早、更便宜的成本控制 | 已有铁律，需在 review 中守住 |
| **CI 指标对齐 `cicd.*`** | semconv 已有 `cicd.pipeline.*` / `cicd.pipeline.task.*` / `cicd.worker.*`（Release Candidate），可用于统一 CI 观测的命名 | 待评估 |

关于第三点：CI 可观测是商业厂商覆盖最薄的地方——Datadog / Dynatrace 的 CI 能力主要停留在"接 CI 事件"，没有像 Kubernetes 那样的完整语义。我们自建 `ci-workflow-aggregator` 反而有机会**直接用 semconv 的 CI/CD 词汇**，让指标天然可移植。注意该组属性仍是 RC，需锁版本。

### 3.3 需要预留的两件事

1. **trace 二期直接接 OTel SDK**，不要自造上下文传播与 ID 生成。`spec/common-fields.md` 已预留 `trace_id` / `span_id` 注入位，且落盘格式与 W3C trace context 一致，接入时零格式返工。
2. **`gen_ai.*` 只登记、不实现**。若机器人将来调用 LLM，按 `semantic-conventions-genai` 当前定义埋点；会话 ID、工具调用 ID 等高基数值只进日志 / span，禁止进 metric label。

### 3.4 明确不做的四件事

| 不做 | 理由 |
| --- | --- |
| 自研采集 agent / eBPF 埋点 | 已是商品，维护成本远高于收益 |
| 自建 Agentic Ops | 平台商品化 + 我们的故障规模不匹配；先把数据整理干净 |
| 引入重型商业平台 | 成本与锁定风险；现有 Prometheus + Grafana + LTS 足够 |
| 为"AI 可观测"先埋一批高基数指标 | 基数爆炸的代价由我们承担，收益要等真有 LLM 调用再说 |

### 3.5 风险与边界

- **语义约定版本漂移**：`gen_ai.*` 已迁仓、`event.name` 已废弃、`code.filepath` 已改名；映射表必须锁版本（当前锚定 semconv v1.44.0）。
- **`community` 的位置**：请求级可变，只能作日志/指标属性，**不能进 Resource**，否则中心化服务会把整进程数据写死成一个社区。
- **LTS 与 OTLP 生态的适配未验证**：如果把日志迁到 OTLP 后端，需要先确认 LTS 的摄入能力；在验证之前只承诺"可映射"，不承诺"可切换"。
- **自建 CI 观测的维护成本**：aggregator 与事件 agent 是长期负债，命名对齐 semconv 能降低将来替换的成本，但不能消除维护成本。
