# 可观测接入指导

面向**基础设施各类业务**的接入指引：自研微服务、上游开源组件、批处理与平台型作业，都能在本文找到自己的路线。
本文只讲**怎么做**；字段名、取值、命名规则的权威定义在 [spec/](../spec/README.md)，两者冲突时以 `spec/` 为准。

---

## 0. 接入的三条底线

不管走哪条路线，「接入了可观测」的最低标准是三件事同时成立：

| # | 底线 | 判定方式 |
| --- | --- | --- |
| 1 | **日志是结构化 JSON**，单行、UTF-8、字段名符合契约 | 从 stdout / LTS 里取一行，能直接被 JSON 解析器解析 |
| 2 | **暴露 `/metrics`**（Prometheus text 格式），带 `service` / `env` / `instance` / `community` 四个 label | `curl` 该端点返回 200，且有 `_total` / `_seconds` 等指标 |
| 3 | **部署级字段已注入**，四个字段取值恒非空 | 日志里四个字段都在；指标里四个 label 都在 |

只满足其中一两条，等于没接：只有日志没指标 → 查得到原因、画不出趋势；只有指标没日志 → 看得到坏了、查不到为什么；字段不全 → 大盘按 `community` 过滤时**这部分数据静默消失**，且不报错。

---

## 1. 先选路线：你属于哪一类

| 路线 | 典型对象 | 判定方法 | 核心手段 |
| --- | --- | --- | --- |
| **A · SDK 接入** | Go / Python / Node / Java 自研服务 | 代码是我们写的，用的是这四种语言之一 | 直接用 obs-sdk 四个语言包 |
| **B · 非四语言接入** | Ruby / PHP / 其他语言自研或深度定制 | 代码是我们的，但语言不在 SDK 覆盖内 | 官方客户端 + 自写薄插件 + 采集侧日志解析 |
| **C · 组件接入** | Discourse、Etherpad、PostgreSQL、Redis、Nginx 等上游组件 | 代码不是我们的，只有配置权 | 官方 exporter + 黑盒拨测，不改代码 |
| **D · 平台/作业接入** | CI 流水线、定时任务、一次性迁移作业 | 有生命周期、有成功/失败语义，但没有常驻 HTTP 服务 | 事件日志 + Pushgateway 或作业级指标 |

> 一个服务可能同时走两条：例如 CI（D）既有资源层指标（C），又有业务层作业指标（D）。按**观测对象**拆，不按仓库拆。

---

## 2. 接入等级：决定做多深

不是所有业务都要做到同一程度。按风险与用户可见性选档，**至少做到 L1**：

| 等级 | 内容 | 适用 | 工作量 |
| --- | --- | --- | --- |
| **L1 · 可发现** | 结构化日志 + 资源层指标复用 + 存活拨测 | 所有长期运行的服务/组件 | 小 |
| **L2 · 可判断** | L1 + `/metrics`（中间件自动产出的通用指标）+ 四个部署级字段 | 对外提供接口或有明确用户流程的服务 | 中 |
| **L3 · 可定位** | L2 + 业务指标（四黄金信号落在业务语义上）+ 告警规则 + 大盘 | 核心链路、被 SLO 覆盖的服务 | 大 |

「四黄金信号」（延迟 / 流量 / 错误 / 饱和度）出自 Google SRE Book 第 6 章，本仓库的分层目标见 [微服务可观测目标.md](微服务可观测目标.md)；它是**选指标的过滤器**，不是一张必须照抄的清单。

## 3. 路线 A：四语言自研服务

### 3.1 前置

- 拿到对应语言的 SDK 包：`go/`（`github.com/opensourceways/obs-sdk/go`）、`python/`、`node/`、`java/`。
- 确认部署目标会注入 `OBS_ENV` / `OBS_COMMUNITY`（见 §6）。没有这一步，SDK 会兜底成 `unknown`，字段不空但取值无意义。

### 3.2 五步接入

1. **Init 一次**：进程启动时初始化日志与指标，之后全进程复用包级函数/单例。
2. **日志改 kv**：所有日志调用改成「常量 `msg` + 键值对」，禁止 printf 风格。
3. **注册业务指标**：用基础名（不带 `_total` / `_seconds`），中文描述。
4. **挂中间件**：注入 `request_id`、解析 `community`、自动产出通用 HTTP 指标。
5. **暴露 `/metrics`**：把 SDK 的 handler 挂到独立端口或路由上。

### 3.3 各语言最小片段

```go
obslog.Init(obslog.Config{Service: "review", Env: "test", Community: "openEuler"})
obslog.Info("job done", "event", "release", "issue", "2061")
obslog.ErrorContext(ctx, "get account failed", "user_id", uid, "error", err)

m := obsmetrics.New(obsmetrics.Config{Service: "review", Env: "test", Community: "openEuler"})
built := m.NewCounterVec("built_releases", "发布的构建数", "kind")
built.Inc("tag")
http.Handle("/metrics", m.Handler())
```

```python
from obs_sdk import log, metrics

log.init(service="review", env="test", community="openEuler")
logger = log.get_logger(__name__)
logger.info("job done", extra={"event": "release", "issue": "2061"})

metrics.init(service="review", env="test", community="openEuler")
built = metrics.counter("built_releases", "发布的构建数", ["kind"])
built.inc(1, kind="tag")
# GET /metrics → Response(content=metrics.generate_text(), media_type=metrics.content_type())
```

```js
const obs = require('obs-sdk-node');
obs.log.init({ service: 'review', env: 'test', community: 'openEuler' });
obs.log.info('job done', { event: 'release', issue: '2061' });

const m = new obs.metrics.Metrics({ service: 'review', env: 'test', community: 'openEuler' });
const built = m.counter('built_releases_total', '发布的构建数', ['kind']); // Node 用 prom-client 最终名
built.inc(1, { kind: 'tag' });
app.get('/metrics', obs.middleware.metricsRouteHandler(m));
```

```java
ObsSdkConfig cfg = ObsSdkConfig.fromEnvironment(); // 或用 builder 显式指定
ObsLogging.init(cfg);
ObsMetrics m = ObsMetrics.of(cfg);
ObsMetrics.CounterVec built = m.counter("built_releases", "发布的构建数", "kind");
built.inc("tag");
```

完整用法见各语言 README（[go](../go/README.md) / [python](../python/README.md) / [node](../node/README.md) / [java](../java/README.md)），部署形态约定见 [AGENTS.md](../AGENTS.md)。

### 3.4 路线 A 的四条硬约定

- **`msg` 是常量短语，取值走 kv**。`msg` 一旦嵌值，每一行都不同，LTS 无法按 `msg` 聚合，日志告警静默失效。
- **业务指标名带 `<service>_` 前缀；中间件公共指标（`http_server_*`）不加任何前缀**。原因见 [spec/metrics-format.md](../spec/metrics-format.md)。
- **禁止高基数 label**：`request_id` / `trace_id` / `span_id` / 用户 ID / 订单号一律不进 label，会撑爆时序基数。
- **`community` 只在可信判定点解析**（路由前缀 / 认证主体 / 白名单），禁止裸读 URL 或 Header。

## 4. 路线 B：非四语言服务

代码是我们的，但语言不在 SDK 覆盖内（当前典型：Ruby on Rails 的论坛）。**核心原则：只挂在上游的扩展点上，不 patch 业务代码。**

### 4.1 指标

1. 优先找**官方/社区维护的 Prometheus 插件或 exporter**（例如 Discourse 的 `discourse-prometheus`）。
2. 没有官方插件时，用该语言的官方 Prometheus 客户端自己建 registry 与 HTTP 端点；**薄封装**，不做自研 instrumentation。
3. 业务指标通过该生态的**插件注册点**注入（例如 Discourse 的 `global_collectors`），不要改核心文件。
4. 暴露出来的时间序列**必须补齐** `service` / `env` / `instance` / `community` 四个 label，与 SDK 服务口径一致，否则无法并入同一批大盘。

### 4.2 日志

上游日志格式通常不可配、且把取值写进 `msg`（与改造前的 logrus 文本行同构）。做法是**在采集侧转换**：

- 用 log-agent（fluent-bit）挂 `parser` / `lua` filter，把文本行解析成 JSON；
- 补齐四个部署级字段；
- 能稳定提取的维度（路径、状态码、耗时、控制器）映射成独立字段；
- **不要**为了统一格式去改上游代码——升级即失守。

### 4.3 一个具体例子：Discourse

| 层 | 做什么 | 是否改核心 |
| --- | --- | --- |
| 资源层 | 复用 cAdvisor / node-exporter / kube-state-metrics | 否 |
| 运行时 | 官方 `discourse-prometheus` 插件（`http_*`、`sidekiq_*`、GC），注意它是独立 collector 进程（默认 `localhost:9405`），不是应用端口的 `/metrics` | 否 |
| 业务指标 | 自写小插件注册到官方 `global_collectors`，只打发帖/登录/搜索/上传几条关键旅程 | 否 |
| 日志 | fluent-bit 解析 Logster 文本行 → JSON → LTS | 否 |
| 端到端 | blackbox 探 `/`、`/latest`；带 API key 的合成事务 | 否 |

### 4.4 路线 B 的验收

与路线 A 完全一致的三条底线，外加一条：**升级上游版本后重跑一遍契约检查**（指标名还在、日志字段还在、取值没变成全零）。

## 5. 路线 C：上游开源组件与中间件

### 5.1 优先用官方 exporter，不自研

| 对象 | 推荐 | 说明 |
| --- | --- | --- |
| 主机 / 容器 / K8s 对象 | node-exporter、cAdvisor、kube-state-metrics | 平台侧统一部署，业务**不要重复采集** |
| PostgreSQL | `postgres_exporter` | 连接数、慢查询、复制延迟 |
| Redis | `redis_exporter` | 内存、命中率、阻塞、连接 |
| Nginx / Ingress | `nginx-prometheus-exporter`、ingress-nginx 自带指标 | 4xx/5xx、上游延迟 |
| 任意 HTTP 端点 | `blackbox_exporter` | 可用性、证书到期、首字节时间 |

### 5.2 组件指标不改名

组件指标保留官方名称（`pg_up`、`redis_connected_clients`），靠 `job` / `component` / `namespace` 等抓取侧 label 区分实例。**不要**给它们套 `<service>_` 前缀——那是自研业务指标的规则。

### 5.3 黑盒拨测是零侵入的第一道防线

对任何对外提供服务的组件，先加一条探活：

- 探什么：真实用户入口（`/`、登录页、健康检查路径），不是 `localhost`；
- 从哪探：**集群外**（用户视角）；
- 判什么：状态码、TLS 证书剩余天数、响应时间 P95；
- 注意：探活失败要先排除「目标没暴露」而不是直接判故障。

### 5.4 组件的日志

同样走 stdout → log-agent → LTS，**采集侧解析**。组件自带的访问日志/错误日志是文本，解析规则要跟着组件版本走，升级时记得回归。

## 6. 部署侧：四个字段的注入

### 6.1 解析链

`service` / `env` / `instance` / `community` 四个字段统一按三级解析：

**显式参数 > 环境变量（`OBS_SERVICE` / `OBS_ENV` / `OBS_INSTANCE` / `OBS_COMMUNITY`）> 内置默认**

内置默认是契约值：`service` / `env` / `community` = `unknown`，`instance` = hostname（k8s 下即 pod 名）。

> ⚠️ **四个字段取值恒非空**。空值不会输出成 `unknown`，而是让日志 JSON 里**整条键消失**、指标 label **整段跳过** —— 采集侧按字段建索引/过滤时静默漏数，且不报错。少一级兜底，等价于这个字段没接进来。

### 6.2 取值从哪来

| 字段 | 值 | 来源 |
| --- | --- | --- |
| `service` | `service.yaml` 里的服务名 | 代码 Init 写死（推荐）；`OBS_SERVICE` 用于多环境同镜像 |
| `env` | `prod` / `test` / `preview` / `staging` | 部署注入；`service.yaml` 里的 `prod-02`、`prod-github` 需归一到 `prod` |
| `instance` | pod 名 | 默认 hostname，**不用注入** |
| `community` | [community-values.md](../spec/community-values.md) 的枚举，**统一小写** | 部署注入；请求级可覆盖 |

`env` / `community` **必须由部署侧注入**：namespace 推不出（同一社区 prod/test 同名）、集群名是 ArgoCD 规范名（pod 内无法自省）、pod 名也不含这些信息。

### 6.3 helm values 片段

```yaml
env:
  - name: OBS_ENV
    value: prod
  - name: OBS_COMMUNITY
    value: openEuler
```

注入位置是各部署目录 `values.yaml` 中对应 workload 的 `env` 块。**核对时必须按 App 的 `sources[].repoURL` 认准 values 仓**——组织内存在同名仓，只看一个仓会得出「未注入」的错误结论。

### 6.4 注入后自查

- `kubectl exec <pod> -- env | grep OBS_` 四个值都在；
- 日志里四个字段都有值；
- `curl /metrics | grep community` 四个 label 都在。

## 7. 暴露与采集

### 7.1 `/metrics` 端点

- 路径固定 `/metrics`，Prometheus text 格式（`Content-Type: text/plain; version=0.0.4`）。
- 端口独立于业务端口优先（便于网络策略与抓取配置收敛）；挂在业务端口上也可以，但要确认网关/鉴权不拦。
- **`/metrics` 抓取本身不应当计入业务指标**：在通用 HTTP 指标与大盘查询里排除该路径（例如 `path!="/metrics"`）。实测自采约占请求量 1/3，不排除会污染 QPS 与错误率。

### 7.2 指标抓取

各集群 Prometheus Agent 用 `kubernetes_sd_configs` 直抓，**不依赖 ServiceMonitor CRD**，再 `remote_write` 到中心 Prometheus。

抓取侧三条纪律（细则见 [spec/metrics-format.md](../spec/metrics-format.md)）：

1. 抓本 SDK 输出的 job **一律 `honor_labels: true`**，否则服务暴露的 `instance` 会被抓取地址顶掉；
2. **不要**把 `__meta_kubernetes_service_name` 映射成 `service`（与 SDK 的 `service` 正面冲突）；
3. `namespace` / `pod` 可以照打，`honor_labels` 逐 label 生效。

### 7.3 日志采集

stdout → log-agent（fluent-bit，`allContainers: true` 全量采集）→ LTS。**服务只要写 stdout 就进 LTS**，不需要新增采集策略。

要让日志在 LTS 里可检索/可聚合，还需要：

- **结构化解析**只针对契约 JSON 配规则（云端结构化或 ICAgent 结构化**二选一**，切换必须先删旧配置）；
- 结构化配置**只对新增日志生效**，历史数据不会重解析；
- 一个日志流只能配一种结构化方式，改之前先确认没有别的服务在用。

### 7.4 别把采集噪声当业务信号

抓取与探活都会产生流量和日志。接入后先在流里看一眼：如果 error 大头是 `/metrics` 抓取产生的（如 `not a excepted url: /metrics`），那是框架噪声，在大盘与告警侧排除，不要改业务代码。

## 8. 埋什么：指标从四黄金信号选

| 信号 | 自研服务 | 组件/平台 |
| --- | --- | --- |
| **延迟** | 通用层由中间件自动产出 `http_server_*`；业务层按关键操作补 | 组件 exporter 自带（如 DB 查询耗时） |
| **流量** | 请求数 / 业务事件数（如发布数、签署数） | 事务率、队列长度 |
| **错误** | 显式 5xx + 隐式（200 但业务失败）+ 策略性口径 | 上游错误码、重试次数 |
| **饱和度** | goroutine / 连接池 / 队列积压 | CPU、内存、磁盘、连接数 |

**分两层埋**：

- **通用层（T0）**：接口级 QPS / 错误率 / P95，由中间件零埋点产出，**不要手写**；
- **业务层（T2）**：3~9 个指标，覆盖核心用户旅程。先用一句话写清「这个指标回答什么问题」，答不上来的不要埋。

**命名与 label**：业务指标 `<service>_<subsystem>_<name>_<unit>`；只加低基数维度（`kind`、`result`、`status`、`method`）；`community` 由 SDK 自动补，不要手写。

## 9. 上线检查清单

### 9.1 接入前（设计阶段）

- [ ] 选定了路线（A/B/C/D）与接入等级（L1/L2/L3）
- [ ] 列出了本服务的 3~9 个业务指标，每个都能对上四黄金信号之一
- [ ] `community` 的判定点写清（哪个路由前缀 / 认证主体 / 白名单）
- [ ] 部署目标确认会注入 `OBS_ENV` / `OBS_COMMUNITY`

### 9.2 发布时（代码与配置）

- [ ] 日志全部 kv 传参，无 printf 残留，`msg` 是常量
- [ ] Init 只调用一次，且 service 名与 `service.yaml` 一致
- [ ] `/metrics` 可访问，且不被鉴权/网关拦截
- [ ] 中间件已挂载，`request_id` 有值
- [ ] values 仓（按 App 的 repoURL 认准）已加 `OBS_*`

### 9.3 上线后 24 小时内（验证）

按**三步法**验证「真的接进来了」，不要只看 CI 绿：

1. **进程里确实有**：`grep` 二进制/依赖，确认 SDK 被链接；
2. **端点确实在**：`curl /metrics` 返回 200，随便请求一个不存在的路径也应返回 200（说明抓取路由没被业务路由抢走）；
3. **数据确实出**：触发一次真实业务事件，确认对应指标的 series 出现、对应字段的日志可检索。

> ⚠️ **指标不存在 ≠ 没接入**：多数客户端库是**懒初始化**，零流量时该指标在 `/metrics` 上完全不出现。三步法里第 3 步就是为这个设计的。

- [ ] 日志在 LTS 可检索，四个字段齐全
- [ ] 指标在中心 Prometheus 可查，四个 label 齐全
- [ ] 大盘能看到本服务；告警规则已配置并演练过一次
- [ ] 确认 `/metrics` 自采流量已被排除

## 10. 故障速查

| 症状 | 最常见原因 | 处理 |
| --- | --- | --- |
| `/metrics` 404 | 路由没挂 / 被业务路由抢占 / 网关拦截 | 第 2 步验证；换独立端口 |
| 指标「不存在」 | 懒初始化 + 零流量 | 触发一次真实事件再看 |
| 指标在，但被改名成 `exported_instance` | 抓取 job 没开 `honor_labels: true` | 改 Agent 配置 |
| `community` 是 `unknown` | 部署侧没注入 / 注入值为空 | 查 Pod env；按 §6.4 自查 |
| 日志里某个字段整条消失 | 取值为空（不是「显示成空串」） | 补齐兜底链 |
| 日志是文本行，无法聚合 | 还没接 SDK，或上游格式不可配 | 路线 A/B；采集侧解析 |
| 大盘查不到某服务 | 抓取 job 选错 namespace/端口；`remote_write` 未通 | 查 target 状态与中心写入 |
| 日志 error 数量异常高 | `/metrics` 抓取噪声 | 在大盘/告警侧排除该路径 |
| 指标基数暴涨 | 把 ID 类字段当了 label | 删除高基数 label，改用日志检索 |

## 11. 可以不接的情形

以下情况允许只做到 L1，但需要在服务清单里登记说明：

- 一次性作业（迁移、巡检脚本）且无长期运行语义；
- 由父服务完全覆盖的编排子仓（例如 `meeting-server` 这类只做部署编排、自身无业务逻辑）；
- 纯静态资源或托管服务（由平台侧指标覆盖）。

即使不接业务指标，**L1 的日志与存活探测仍要做**——否则出问题时连「它还在不在」都答不上来。
